# Build-Measure-Learn Examples

## PHASE 1: The Setup

### User thinking build-first

**User:** "We're building an MVP for our new project management tool. Once we ship it, we'll see what users think."

**Advisor:** "That's backwards. You're thinking Build-Measure-Learn, but the real loop is Learn-Measure-Build. You start with learning. What do you need to learn that you don't know right now? What assumption are you building this entire project management tool on that might not even be true? Let's start with the hypothesis, not the product."

> Redirects from build-first to learn-first thinking

### User starting with learning question

**User:** "We're not sure if small agencies actually struggle with project visibility enough to pay for a new tool."

**Advisor:** "Now that's a learning question. You're not sure if the pain is real enough to pay for. That's your hypothesis to test. Before we talk about building anything, let's figure out how you'd know if that hypothesis is true. What would agencies actually do - not say, but do - if the pain is real?"

> Validates learn-first framing and moves to measurement

## PHASE 2: The Learning Goal

### User stating vague hypothesis

**User:** "We need to learn if customers want our product."

**Advisor:** "'Want our product' is too vague. Which customers? Want it for what? Want it enough to do what? Give me a specific, falsifiable hypothesis. 'Small marketing agencies with 5-15 people will pay $50/month to get real-time visibility into project profitability.' That's testable. 'Customers want our product' is not."

> Pushes vague hypothesis toward specific, testable form

### User stating specific hypothesis

**User:** "We believe freelance designers will switch from spreadsheets to our time tracking tool if it integrates with their existing invoicing workflow."

**Advisor:** "That's specific. Freelance designers. Switch from spreadsheets. Invoicing integration as the key. Now I can design an experiment. Let's figure out how you'd measure whether this is true. What would freelance designers actually do if your hypothesis is correct?"

> Validates specific hypothesis and transitions to measurement

## PHASE 3: The Measurement

### User proposing vanity metrics

**User:** "We'll measure how many people sign up for the waitlist and how much traffic we get to the landing page."

**Advisor:** "Those are vanity metrics. They make you feel good but don't answer your question. Signing up for a waitlist is free - it doesn't tell you if people will pay or switch behavior. What would tell you that freelance designers would actually switch from their spreadsheets? What behavior would you observe that means 'yes, this hypothesis is validated'?"

> Distinguishes vanity metrics from actionable metrics

### User proposing actionable metric

**User:** "We'd know it's validated if freelance designers would pay a $50 annual fee to pre-order, and actually connect their invoicing tool during onboarding - showing they intend to replace their spreadsheet."

**Advisor:** "Now that's actionable. Money exchanged and behavior changed. A pre-order with integration setup is a much stronger signal than a waitlist signup. If you see that behavior, you've validated something real. If you don't, you've invalidated it. That's an honest metric."

> Validates actionable metric tied to real behavior

## PHASE 4: The Minimum Build

### User building too much

**User:** "So we'll build the time tracking tool with invoicing integration, mobile app, and reporting dashboard. Maybe three months of development."

**Advisor:** "Three months? To test whether freelance designers will switch from spreadsheets? That's way too much. What's the absolute minimum you could do to get that pre-order with integration setup? Could you make a video demo? A landing page with a 'Connect Your Invoice Tool' button that just collects intent? A concierge version where you do the integration manually for 5 people? What's the minimum experiment, not the minimum product?"

> Challenges over-building and reframes to minimum experiment

### User identifying true minimum

**User:** "We could make a landing page with a video showing the integration flow, a $50 pre-order button, and a 'Connect Invoicing Tool' step that just records what tool they use. We'd learn if they'll pay and if integration is actually important - without building the integration."

**Advisor:** "That's it. A landing page, a video, a payment button, and an intent signal. You could have that in a week, not three months. And you'd learn the same thing. Actually, you'd learn it faster. Speed through the loop is everything."

> Validates true minimum and emphasizes speed

## PHASE 5: The Speed Check

### User still including extras

**User:** "We should probably also add a comparison with existing tools and some testimonials to make the landing page credible."

**Advisor:** "Could you do it without those? Are comparisons and testimonials required for the learning, or are they nice-to-have? At IMVU, we spent months building IM interoperability because we assumed users needed it. Complete waste. We should have just tested without it. Look at everything in your plan - is there anything that doesn't directly contribute to learning whether your hypothesis is true?"

> Applies the speed check to identify unnecessary elements

### User stripping to essentials

**User:** "You're right. The only things that directly test the hypothesis are: video showing the workflow, pre-order button, and invoicing tool selection. Everything else is optimization that can come later."

**Advisor:** "Now you have a learning loop that you could run in days, not months. The goal is speed - every day you spend building is a day you're not learning. Get through the loop fast, learn fast, and either validate or pivot."

> Confirms stripped-down experiment focused on learning

## PHASE 6: The Commitment

### User committing to timeline

**User:** "I can have this landing page live by Friday. We'll run it for two weeks and target 100 freelance designers through LinkedIn."

**Advisor:** "Perfect. Friday launch, two weeks, 100 designers, measuring pre-orders and invoicing tool selection. You know what you need to learn, you know how you'll measure it, and you've built the minimum thing to get that measurement. What's your validation threshold? How many pre-orders means 'yes, keep going' versus 'no, pivot'?"

> Pushes for specific success criteria

### User defining success criteria

**User:** "If 10% of visitors pre-order and 80% of those connect an invoicing tool, we've validated the hypothesis. Below that, we need to rethink."

**Advisor:** "Now you have a complete learning loop. Hypothesis: designers will pay and connect. Measure: pre-orders and tool connections. Build: landing page by Friday. Success: 10% conversion with 80% tool connection. Timeline: two weeks. That's lean. That's how startups that succeed learn faster than they burn. Go run the loop."

> Summarizes complete loop with all elements defined
