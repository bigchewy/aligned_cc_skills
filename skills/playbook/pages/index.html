Product

Decide what to build next, cut it to fit, design it on one system, check it is safe, and ship it.

  • Start hereFrame, Shape, Bet

    A team needs a product roadmap, has a draft roadmap or feature list with no sense of what fits, faces a launch or contract date that can't move, has made promises to customers that aren't on the calendar, or keeps letting projects run over.

  • Working Backwards

    A team needs to define a new product or feature by writing the press release first and working backwards to what must be built.

  • Getting Real Cut

    A version one or a new feature has a long list and needs cutting before the build, a design keeps growing, settings or scale work are creeping in, or the founder can't say what the product can't live without.

  • User Story Map

    A team is about to design screens for a product or feature, earlier screen designs started from features, pages, or access rules and missed what users do, more than one role (such as a member and a facilitator) shares the product, the team can't agree what the first release must include, or someone needs a story map built and agreed before any screens.

  • Breadboard to Pages

    A breadboard or Slice 1 of a story map is agreed and needs finished screens to guide the build, an AI agent keeps inventing styles instead of using the design system, screens were drawn with placeholder content or only the happy path, or someone needs each screen tied back to the place and action it comes from.

  • FEW HICCUPPS Review

    A design doc is about to be built and its claims about the codebase need checking against the code, the tests all pass but nobody has asked what they miss, a feature needs its edge cases and failure modes found before the build, or an existing screen feels wrong and nobody can say which expectation it breaks.

  • Design Principles

    Someone needs guiding design principles for a product that prioritize simplicity, elegance, and user experience.

  • Interface Inventory

    An existing app has grown several looks for the same job (buttons, grays, text fields), an AI agent has been inventing styles, someone is about to redesign or write design principles for an app that already exists, or the UI feels inconsistent and nobody can say where.

  • Logic Check

    A screen looks amateur and nobody can say why, an AI agent keeps picking colours, sizes, or weights by feel, a design principles file needs checking before screens are built from it, or text contrast, button hierarchy, or colour-only signals need checking.

  • Four Question Threat Model

    A design or feature touches login, permissions, user data, row-level security, secrets, webhooks, a third-party API, or a Claude Code hook, plugin, or MCP server, and nobody has asked what can go wrong before it ships.

  • PHANTOM-B LLM Threats

    A feature, hook, plugin, or agent sends text to an LLM and acts on what comes back, reads text someone else wrote (emails, PRs, web pages, tool results), or lets the model call tools, and nobody has asked what can go wrong with the model part.

  • Assigning AI Roles

    Someone is building an AI tutor, AI coach, role-play practice partner, or AI feedback tool for a course or program; an existing AI learning tool gets good ratings but behavior does not change; or a team needs to decide what the AI should and should not do for learners.
