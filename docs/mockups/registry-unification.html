Registry Schemas architecture

Two YAML registries serve as the single source of truth. Both use flat lists (no nesting by category) for easy append, sort, and query. Grouping happens at query time by consumers.

Advisor Registry advisors/registry.yaml

Replaces the existing advisors/registry.md markdown format. Serves both LLM context windows and programmatic consumers (auto-router build script).

  • Required fields: id, name, summary, prompt, domains
  • Optional fields: evaluation_expertise, best_for, not_for, note
  • Selection guidelines: Embedded in YAML with scope rules, hard-exclude logic, and calibration examples
  • Unprofiled advisors: Minimum viable entries with empty optional fields and a note field

Framework Registry frameworks/registry.yaml

New file covering all 138 frameworks. Token budget: ~50 tokens per entry, ~7,000 total. Fits comfortably in LLM context windows.

  • Required fields: id, name, advisor, purpose, category, domains, use_when
  • Optional fields: required_documents, helpful_documents
  • Category: Free-form string (not enum) from a starter set of 16 categories
  • Advisor field: Singular, because every prompt.md opens with one advisor voice

Schema Decisions D1-D10

Architect-validated decisions shaping the registry format.

#DecisionRationale
D1YAML over JSON or markdownServes LLM + programmatic consumers. ~3x more token-efficient than prose markdown.
D2Centralized single file per registryDiscovery requires reading one file, not 138.
D3Flat list, no nesting by categoryEasier to append, sort, query. Grouping at query time.
D4advisor field stays singularEvery prompt.md opens with one voice.
D5triggers not in registryAuto-router generates these from registry data + LLM.
D6Selection guidelines stay in YAMLOnly consumer is critique-panel-orchestration.
D7READMEs via LLM skill steps, not scriptsNo yq dependency. Trade-off: non-deterministic. Acceptable for reference docs.
D8Derived artifacts on-demand onlyNot coupled to add-advisor/add-framework. Avoids latency and failure modes.
D9category is free-formNo consumer filters by category today. Controlled vocabulary adds maintenance with no payoff.
D10Don't consolidate add-advisor Steps 3 and 8bDifferent targets (project-local vs plugin registry), different audiences.

Deferred: Contextual Recommendation follow-up design

Contextual recommendation for use-advisor and use-framework is deferred to a separate design. The registry migration enables this feature by providing the metadata (domains, use_when, best_for) needed for scoring, but the recommendation behavior has its own edge cases, interaction design, and testing surface.

Follow-up Design Scope

The follow-up design should address:

  • Three-path behavior: Named (fuzzy match), contextual (intent scoring), bare (listing)
  • Scoring heuristic: Which fields to weight and how
  • Context detection: How to distinguish contextual from bare invocations
  • Unprofiled advisors: ~55% of catalog lack best_for / evaluation_expertise
  • Fallback: Handling zero or weak matches from scoring
  • Acceptance criteria: Recommendation quality thresholds

Relationship to This Design

The registry migration creates the prerequisite data layer. Contextual recommendation consumes it.
