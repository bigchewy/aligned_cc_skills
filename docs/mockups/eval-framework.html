System prompts use advisor prompts and framework prompt.md — never SKILL.md. Post-critique revision.

ArchitectureCore

The eval architecture centers on Promptfoo as the eval runner, a three-provider comparison model, and a structured pipeline from scenario YAML through to scored reports. System prompts are composed from advisor prompts and framework prompt.md files — the behavioral content that shapes LLM output. SKILL.md files are never used as system prompts; they contain Claude Code orchestration instructions meaningless in direct API calls.

Three-Provider Comparison FlowFlowchart

Every scenario runs the same input through three providers to isolate the value of structured skill definitions. The comparison answers: does having the full framework definition produce meaningfully better output than vanilla or knowing the framework name?

  • Provider A (Full Stack) — System prompt contains the advisor prompt and/or framework prompt.md — the behavioral content that shapes LLM output. SKILL.md files are NOT used; they contain Claude Code orchestration instructions meaningless in direct API calls.
  • Provider B (Vanilla) — Minimal system prompt: "You are a helpful assistant." Same user prompt, no methodology. Represents most LLM users.
  • Provider C (Aware But Unaided) — No system context, but the user prompt names the framework explicitly. Represents a competent ChatGPT user who knows what to ask for but lacks the structured definition.
  • Key insight — A vs. C is the defensible claim. If Provider C scores nearly as well as A, the skill isn't earning its place.

Eval PipelineFlowchart

The end-to-end pipeline from scenario definition through API execution to scored reports. Promptfoo orchestrates the middle steps; we own the scenario configs and scoring rubrics. The distinctness scorer runs as a post-processing step on the results JSON, not as an inline assertion — Promptfoo assertions receive single outputs, but pairwise comparison requires all persona outputs simultaneously.

  • Scenario YAML — Declares providers, fixtures, rubrics, and metadata. Adding a new skill to eval means writing one YAML file.
  • Promptfoo Runner — Handles API calls, parallel execution, and result collection. No custom harness code needed.
  • LLM-as-Judge — Pinned judge LLM (specific model + temperature 0) scores each output against weighted rubrics (1-5 scale). Pinning prevents judge variance from exceeding the 0.5-point regression threshold.
  • Post-Processing — distinctness.py runs AFTER eval completes, against the results JSON. Parses persona sections, computes pairwise cosine similarity via embeddings.
  • Reports — JSON/CSV export plus shareable web UI. Summary reports committed; raw logs gitignored.

Repo StructureReference

The eval suite lives inside the main repo under e2e/. Scenario configs are co-located with the skills they evaluate for transparency and discoverability. Post-critique additions: baselines/ for regression tracking, tests/ for scorer unit tests, and trigger-map.yaml for CI/CD path mapping.

  • scenarios/ — One subdirectory per skill type, one YAML file per scenario
  • fixtures/ — Synthetic but realistic content (200-400 words each) used as evaluation inputs
  • scorers/ — Custom Python scorers (only distinctness.py for V1)
  • tests/ — pytest unit tests for scorer code (test_distinctness.py covers success, error, and edge cases)
  • baselines/ — JSON baseline scores from last passing run on main; populated by first passing run
  • trigger-map.yaml — Static mapping of changed paths to affected scenario files for CI/CD
  • reports/ — Committed summary reports; raw logs gitignored
  • README.md — MVE: setup instructions. Post-MVE: full methodology documentation

ScoringRubrics

LLM-as-judge rubrics provide the primary scoring mechanism. The judge LLM is pinned to a specific model with temperature 0 to ensure reproducible scoring. Success criteria are split into MVE (must prove before expanding) and post-MVE tiers.

Rubric DimensionsScoring

Six common rubrics are available to all scenarios. Each scenario selects relevant rubrics and assigns weights based on which quality dimensions matter most for that skill type.

  • Specificity — Concrete references to the input content vs. generic advice
  • Actionability — Executable recommendations vs. vague direction
  • Methodology Accuracy — Correct framework execution vs. hallucinated steps (Provider C's weakness)
  • Perspective Diversity — Distinct viewpoints vs. collapsed consensus
  • Completeness — All framework phases addressed vs. gaps
  • Voice Consistency — Advisor-specific voice and patterns vs. generic LLM tone

Judge LLM ConfigurationPinned

The judge LLM must be pinned to a specific model and temperature to prevent judge variance from exceeding the 0.5-point regression threshold. If Anthropic deprecates the pinned model, update the config explicitly — do not allow auto-migration.

  • Model — Pinned to a specific Claude version (e.g., claude-sonnet-4-20250514) in promptfooconfig.yaml
  • Temperature — Set to 0 for deterministic scoring across runs
  • Configuration — Set via defaultTest.options.provider in the master config, applies to all llm-rubric assertions
  • Rationale — Without pinning, model updates or temperature drift could cause score fluctuations that mask real quality changes or trigger false regressions

Distinctness ScorerPost-Processing

Inter-persona distinctness is not handled by Promptfoo natively. A custom Python scorer computes pairwise cosine distance across persona outputs using embeddings. This runs as a post-processing step, not an inline assertion — Promptfoo custom assertions receive a single output per invocation, not all provider outputs simultaneously.

  • Timing — Runs AFTER promptfoo eval completes, against the results JSON
  • Parsing — Extracts per-persona sections from full-stack provider output (persona-panel outputs are structured with persona headers)
  • Embeddings — Pairwise cosine similarity using OpenAI text-embedding-3-small (chosen for cost — distinctness measurement doesn't need large embeddings)
  • Threshold — Cosine similarity > 0.92 between any two personas = fail
  • Output — Returns pass/fail plus similarity matrix, appends to eval report
  • Size — ~80-100 lines including JSON parsing and error handling. The only custom code in the eval suite.

Pass/Fail ThresholdsCalibration

Starting thresholds for ship/kill decisions. These are initial values to be calibrated after the first few runs.

  • Full-stack vs. vanilla delta — Must be +1.0 or higher average across rubrics
  • Full-stack vs. aware-but-unaided delta — Must be +0.5 or higher (the harder bar)
  • Absolute full-stack score — Must be 3.5/5.0 or higher average
  • Inter-persona distinctness — Cosine similarity must be below 0.92 for all pairs

Success CriteriaTiered

Success criteria are split into two tiers. MVE criteria must be proven before expanding scope. Post-MVE criteria are valuable but depend on the ship/kill signal working first.

MVE — Must prove before expanding

  • Ship/kill signal — For any skill, the eval produces a quantitative score comparing skill-aided output vs. vanilla output across defined rubrics. A skill that doesn't meaningfully outscore vanilla on at least one dimension fails.

Post-MVE — Prove after ship/kill signal works

  • Regression detection — When skill markdown changes, CI runs catch quality degradation before merge.
  • Methodology as marketing — The eval repo structure, scenario definitions, and README are publishable. A technical evaluator can read the methodology and conclude the tools are validated rigorously.
  • Generalization — Adding a new skill to the eval suite means writing a scenario YAML file and fixture content, not modifying harness code.

Error HandlingResilience

Failure modes for the judge LLM and embedding API, with explicit policies for each. The core principle: fail-closed for judge errors (no ambiguous pass), graceful degradation for embedding errors (fallback to LLM-as-judge perspective-diversity rubric).

Judge LLM Failure ModesFail-Closed

Judge failures are handled with a fail-closed policy. An eval run with any errored scenarios cannot produce a passing result — ambiguity never counts as success.

  • API errors (rate limit, timeout, 500) — Promptfoo retries automatically. Set to 2 retries with exponential backoff via defaultTest.options.retry.
  • Unparseable response (no score extractable) — Assertion fails with JUDGE_ERROR. Scenario is marked errored, not failed. Errored scenarios do not count toward pass/fail thresholds but are flagged in the report.
  • Policy: fail-closed — An eval run with any errored scenarios cannot produce a passing result. This prevents ambiguous passes from slipping through.

Embedding API Failure ModesGraceful Degradation

Embedding failures in the distinctness scorer degrade gracefully — the perspective-diversity rubric (LLM-as-judge) provides a fallback signal. The scorer logs which persona pairs were not compared so the gap is visible.

  • API unreachable — Distinctness check is skipped with a warning. The perspective-diversity rubric provides fallback coverage.
  • Logging — Scorer logs which persona pairs were not compared so the gap is visible in the report.
  • Unparseable persona sections — Scorer reports "unparseable" and skips. Does not fail the run.
  • All personas identical — Scorer fails with similarity matrix showing 1.0 across all pairs (this is a real failure, not an error).

CI/CDPost-MVE

GitHub Actions triggers scoped evals when skill files change in PRs, and runs full-suite evaluations weekly to catch model-level regressions. Path-to-scenario mapping uses a static trigger-map.yaml file. Baseline scores are stored as JSON in e2e/baselines/ and committed to git.

PR Change Detection FlowCI/CD

When files in skills/, advisors/prompts/, or frameworks/ change in a PR, GitHub Actions reads trigger-map.yaml to map changed paths to affected scenarios, runs scoped evals, and gates the merge on threshold checks against baselines.

  • Path mapping — trigger-map.yaml defines static mappings from changed paths to scenario files. No runtime YAML parsing or dynamic file-reference resolution needed.
  • Scoped execution — Only affected scenarios run, typically 2-6 API calls per PR
  • Threshold comparison — Scores compared against baseline JSON in e2e/baselines/; any metric dropping >0.5 points fails the check with a diff report
  • Weekly full run — Full suite against latest Claude model version, catches model-level regressions. Updates baselines only if all scenarios pass.

Trigger MapPost-MVE

A static YAML mapping file (e2e/trigger-map.yaml) defines which changed paths trigger which scenario files. The GitHub Actions workflow reads this map, computes the intersection with the PR's changed files, and runs only the matched scenarios. This avoids runtime YAML parsing or dynamic file-reference resolution.

  • Format — List of triggers, each with paths (glob patterns) and scenarios (file paths)
  • Example — Changes to advisors/prompts/april-dunford.md trigger both the use-framework and use-advisor scenarios that reference her
  • Maintenance — When adding a new scenario, add a corresponding entry in trigger-map.yaml

Baseline StorageRegression

Baseline scores are stored as JSON in e2e/baselines/ and committed to git. PR workflows compare against these files. Bootstrap: the first eval run for a new scenario has no baseline — it passes unconditionally and writes the initial baseline on merge.

  • Location — e2e/baselines/<scenario-name>.json, committed to git
  • Bootstrap — First run for a new scenario has no baseline, passes unconditionally, writes initial baseline on merge
  • Updates — After a passing eval on main, CI writes current scores to baselines. Weekly runs update baselines only if all scenarios pass.
  • Regression gate — Any metric dropping >0.5 points vs. baseline fails the PR check

Skill Type Taxonomy4 Patterns

Every skill maps to one of four eval patterns. Patterns 1-3 cover the bulk of the plugin's value surface (65 advisors, 138 frameworks, persona-panel). Pattern 4 is deferred to V2. These are descriptive framing for organizing scenarios, not a prescriptive schema — revise if the first three MVE scenarios reveal a pattern doesn't hold.

Four Eval PatternsTaxonomy

Each pattern defines the provider configuration, fixture type, key rubrics, and any custom scorers needed. Adding a new skill to eval means identifying its pattern and writing a scenario YAML.

  • Pattern 1: Single Advisor Critique — use-advisor with any of 65 advisors. System prompt: advisor prompt file. Key rubrics: domain specificity, voice consistency, insight quality.
  • Pattern 2: Multi-Persona Evaluation — persona-panel. Key rubrics: perspective diversity, specificity, actionability. Uses distinctness.py as post-processing scorer.
  • Pattern 3: Framework Document Generation — use-framework with any of 138 frameworks. System prompt: framework prompt.md + advisor prompt. Key rubrics: completeness, methodology accuracy. Provider C is strongest differentiator here.
  • Pattern 4: Orchestrated Workflow (V2) — brainstorming, writing-plans, codebase-audit. Multi-agent orchestrations that need multi-turn eval. Deferred.
