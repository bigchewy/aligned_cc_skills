Development PipelinePipeline

The main development pipeline takes an idea from initial scaffolding through design, planning, execution, and branch finishing. Each skill hands off to the next with clear gate conditions.

  • kickstart: Scaffolds a new project with CLAUDE.md, docs structure, eval infrastructure, and design-principles placeholder
  • design-principles: Interactive Steve Jobs persona session to define the project's visual design system
  • brainstorming: Collaborative idea exploration with multi-critic review panels and mandatory visualization
  • writing-plans: Implementation plan with Architect + Verifier dual-critic review
  • executing-plans: Task-by-task execution with checkpoints and verification gates
  • finishing: Deployment audit, code simplification, merge/PR, and plan archival

Business PipelinePipeline

A parallel pipeline for business work — strategy docs, deliverables, and action plans. Shares the advisor critique system with the dev pipeline but uses business-specific critics (Rumelt, The PM).

  • business-brainstorming: Goal → Problems → Root Causes → Solutions sequence with advisor critique panel
  • business-write-plan: Deliverable plan with Rumelt + PM dual-critic review
  • business-executing: Execute plan deliverables with progress tracking
  • business-diagnosis: Lateral tool — invoked when a deliverable is stuck. High severity dispatches 5 analytical sub-agents

Brainstorming OrchestrationCore

The brainstorming skill is the most complex entity in the plugin. It orchestrates project scans, architect auto-consults, visualization generation, multi-critic review panels, and pipeline handoff — all through sub-agent dispatch.

  • Project Scan: Opus sub-agent surveys the codebase and writes findings to /tmp/
  • Architect Auto-consult: Technical questions are proxied to The Architect instead of asking the user
  • Visualization: Session-document-generator dispatches 3 diagram agents in fragment mode
  • Critique Panel: 1-4 advisors selected from registry, with fact-checker + domain critics in parallel

Critique PanelReview

Critics are selected from the advisor registry based on design domain. One critic is designated as the fact-checker (exhaustive claim verification). Others focus on domain-specific criteria from the 9-point checklist. All run in parallel as fresh sub-agents to prevent anchoring.

  • Fact-checker priority: QA Engineer > Architect > first selected critic
  • Division of labor: Fact-checker verifies all codebase claims. Others skip fact-checking entirely
  • Aggregation: Separate sub-agent merges all reports, de-duplicates, orders by severity
  • Round 2: Only if Round 1 found medium/high issues. Scoped to changes only

Advisor SystemArchitecture

The advisor system provides 62 persona prompts organized by domain. Skills consume advisors through the registry for critique panels, auto-consults, and persona adoption. Frameworks (135 total) are composable with advisors for guided interactive sessions.

  • Registry: advisors/registry.md is the canonical source with domains, evaluation expertise, best_for/not_for
  • Prompts: 62 files in advisors/prompts/ — each a complete persona prompt
  • Selection: 1-2 critics for narrow scope, 2-3 typical, 3-4 cross-cutting. Hard-exclude by not_for
  • Frameworks: 135 directories in frameworks/, each with prompt.md and optional examples/anti-examples

Agent Dispatch MapArchitecture

All 11 agents are dispatched by skills via the Task tool. Each agent has a specific model (sonnet for most, opus for critique). Some agents dispatch other agents (e.g., session-document-generator orchestrates 3 diagram agents).

  • Dispatch pattern: Skills use Task tool with subagent_type=general-purpose and full agent prompt
  • Fragment mode: Diagram agents can return structured JSON instead of writing files
  • Fresh agents: Critique sub-agents are always fresh — never resumed — to prevent anchoring
  • Parallel dispatch: Multiple agents launched in a single message for concurrent execution

Hook SystemInfrastructure

Five hook scripts respond to Claude Code lifecycle events. They handle auto-approval of safe operations, eval audit scheduling, error tracking, and usage analytics. Configured in hooks/hooks.json.

  • PreToolUse: Intercepts tool calls before execution — can auto-approve or deny
  • UserPromptSubmit: Fires on every user message — injects context tags into conversation
  • PostToolUse: Fires after tool execution — logs data for analytics
  • PostToolUseFailure: Fires on tool errors — feeds error-diagnosis agent

Maintenance CyclePipeline

The maintenance subsystem finds issues, triages them, and resolves them through the standard dev pipeline. The codebase-audit runs 5 parallel workers; findings flow through a Kanban board before being resolved.

  • codebase-audit: 5 parallel workers (code quality, test quality, security, dead code, architecture)
  • Kanban board: docs/kanban/ with todo, in-progress, done, and did_not_complete lanes
  • kanban-triage: 5-phase root cause analysis per item — CONFIRM, REVISE, or CLOSE
  • kanban-resolve: Orchestrates full triage + fix cycle, invoking dev pipeline skills for actionable items
