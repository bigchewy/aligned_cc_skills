Visualization Runner Extraction + visualize-design Skill

One shared engine for design-doc visualizations — used by brainstorming and a new standalone command

Software brainstorm · 2026-06-11 · aligned plugin · Design doc: docs/plans/2026-06-11-visualization-skill-design.md

Goal

The polished, on-brand visualization you get at the end of a brainstorm is currently locked inside the brainstorming skill. This work frees it: the machinery moves into one shared engine, and a new command — /aligned:visualize-design — lets you produce the same artifact for any document or working thread, anytime. Brainstorming keeps working exactly as it does today, running on the same engine.

What changes

One engine, two callers. The visualization procedure lives in a single shared playbook instead of being buried in brainstorming. A new command renders any markdown doc or conversation thread as a live, on-brand visualization.

Why it matters

Two long-standing annoyances get fixed at the source: the browser now always opens automatically, and every visualization must lead with a plain-language executive overview — no more opening into a wall of implementation detail.

The outcome

Run the new command, watch a self-refreshing visualization build in your browser as you iterate, and get a final polished copy saved to the project when you say it's done. Same look, same quality, no brainstorm required.

The three-piece split follows framework-runner precedent

The extraction mirrors the May 2026 framework-runner refactor: caller-independent procedure moves to skills/_shared/; callers stay thin and own only what is specific to them.

1 · The engine (new)

skills/_shared/visualization-runner.md — token resolution ladder, verbatim copy-and-patch contract, executive-overview rule, widget injection, unconditional browser-open, mermaid gate, strip-script rule, nested sub-tabs rule. Framework-runner house style: Configuration block, fail-closed validation, numbered steps.

2 · The standalone skill (new)

skills/visualize-design/SKILL.md — thin caller. Source resolution (doc path or conversation), session naming, live-session wiring, output to docs/design-visualizations/.

3 · The brainstorming wrapper (slimmed)

skills/brainstorming/references/visualization-protocol.md — stays at its test-pinned path. Keeps only the brainstorming lifecycle: live-update-per-section loop, pre-critique snapshot, post-critique regeneration. Delegates everything else to the engine.

What stays physically where it is

Templates, widgets.html, brainstorm-components.md, and validate-mermaid.mjs (plus its npm dependency) all remain under skills/brainstorming/. The engine takes their locations as configuration inputs. Moving the npm-dependency directory would be blast radius for zero functional gain.

Hard pin The literal path skills/brainstorming/references/visualization-protocol.md is asserted by an e2e test and consumed by both visualizing modes. It must remain a readable file — it becomes the wrapper rather than moving.

Configuration inputs fail-closed

All paths are absolute and resolved by the caller — the brainstorming wrapper resolves its own relative paths; visualize-design resolves from the plugin root. Shared files never self-resolve. Missing or unresolvable config halts with a named error instead of improvising.

Why fail-closed

Two kanban findings (KB-085: browser-open silently skipped; KB-086: goal buried under detail) name two co-equal causes: the agent's compact-direct-write shortcut (hand-writing HTML and never touching the template or protocol) and protocol steps written as skippable prose. The runner answers both — an explicit anti-shortcut contract at every entry point ("copy the file; never hand-write the artifact"), and numbered steps with hard gates that make skipping visible. The browser-open step becomes unconditional and numbered, inherited by every caller from one file. The design claims mitigation of these KBs, not closure — closure is confirmed by observing subsequent sessions.

Produce, then verify

The first tab of every artifact must read at executive altitude: what this is, why it matters, what outcome it produces — plain language a non-engineer scans in under a minute.

1 · Produce — template-guaranteed after commit 2 Today the templates ship an empty skeleton; commit 2 bakes in a pre-built tab bar whose first tab is Overview, with placeholder slots for goal, why-it-matters, and outcome. From then on a verbatim copy carries the structure — fillable, not omittable. No Mermaid, no file paths, no implementation vocabulary on that tab; roughly one screen. Applies from the first live render. This guarantee holds only on the copy path — it is a mitigation complementary to the anti-shortcut contract, not a closed loop.
2 · Verify — pre-snapshot gate, two parts Mechanical sub-check (fail-closed): the Overview panel contains zero mermaid blocks and zero file-path spans — a grep with the same pass/fail contract as the mermaid gate; a match blocks the snapshot until fixed. Semantic self-check (never blocks): altitude and length judged by the LLM with one retry; on a second failure the artifact is written anyway with a one-line message naming the failed check and the slot to edit. A soft judgment never holds the output hostage.
Scope The ban on file paths and diagrams applies to the Overview tab only — detail tabs keep their change tables, file paths, and diagrams.

/aligned:visualize-design new skill

Invoked with an optional markdown file path. With a path: renders that document. Without: renders the validated content of the current conversation. If neither yields enough content, it asks one question rather than improvising.

Session behavior

  • Live by default — same rhythm as brainstorming: self-refreshing /tmp artifact, opened immediately, updated as you iterate.
  • Same brand resolution — project design-principles file, monorepo glob, then global fallback; placeholder files surfaced with a warning.
  • Same template — reuses brainstorming's software template by absolute path (deliberate coupling, Decision 5; divergence deferred until needed).
  • Diagrams — dispatches the same flowchart-generator / architecture-diagram-generator agents brainstorming uses.
  • Finish — on your confirmation: mermaid gate, executive-overview check, write to docs/design-visualizations/{session-name}.html (directory created if missing; an existing file is overwritten — re-rendering is the expected workflow), strip the live-refresh script, open the committed copy.
  • Widgets — injected only when the content actually has a Decision Log or Open Questions section; same flat/categorized thresholds.
  • Not included — critique panel and the Mockups header field; those are brainstorming scaffolding.
