Autopilot Orchestration Redesign

Bash decomposition + plan front-matter manifest + halt-with-reason protocol + mid-flow human-review ban

Brainstorm session 2026-04-30 — drives a writing-plans run targeting docs/ralph_loops/ and skills/writing-plans/. Round 1 critique applied; HIGH-severity items folded in.

Goal

Restructure the Ralph autopilot pipeline so plans declare their environment requirements explicitly, the bash orchestrator decomposes into testable phase scripts, the autopilot halts cleanly with structured reasons instead of crashing, and writing-plans is forbidden from inserting mid-flow "human review" tasks that defeat unattended completion.

The three signals driving this

Signal 1 — Recurring class of failure

Plans reach for MCP tool prefixes that don't load in claude -p. Triggering incidents: mcp__playwright-full__* (ghost namespace) and partially-allowlisted mcp__playwright__browser_resize. Headless can't grant interactive permissions.

Signal 2 — autopilot.sh bloat

642 lines, zero tests, ~70 lines of process-management duplicated with run-ralph.sh. 9 commits since creation are all bug fixes / timeout tuning — no architectural changes. FINISH-BRANCH.md is a 224-line orphan. Verify-gate is triplicated.

Signal 3 — Mid-flow human review

Plans keep inserting tasks like "verify the UI looks correct before proceeding" or "review the interface before Task N+1." The existing Manual Steps Policy uses "manual" too narrowly — judgment-based pauses slip past. The user reviews ONCE at the end.

Success criteria (user's words)

From the brainstorm "I want to know if it will fail and, if there is work to do in advance or after, it should tell me. So there should be clear stages and, if the autopilot isn't going to finish, it should both tell me that upfront and not appear to be erroring out when it hits the stage where I need to do something."
And, post-critique "Another core issue is that you keep writing into the plan that a certain task needs 'human review' before continuing but the whole point is to do the whole thing and then I only look at the end. I never want to review interfaces that are built along the way until the autopilot work is complete."
  • Clear stages — every phase boundary visible.
  • Halt-with-reason — when a stage needs human action, surface it cleanly. Halts are not failures.
  • Pre-flight signal — if a plan won't finish unattended, tell the user upfront.
  • No mid-flow review — review happens once at the end. Never in the middle.
  • Both gates with different jobs — writing-plans validates SHAPE, autopilot validates ENVIRONMENT.

What this design is NOT

  • Not a skill rewrite. Subagents share parent CLI state. The 50-iteration ralph loop depends on per-iteration claude -p process boundaries. That boundary is load-bearing.
  • Not a five-field manifest. Only mcp-tools-required and env-vars-required — the two fields with deterministic machine probes.
  • Not a blocking migration. Manifest is optional in v1; preflight skips when absent.
  • Not a tolerant runner. Plans with mid-flow "human review" tasks are REJECTED at writing-plans time, not silently skipped at execution.

Each phase script declares a typed contract

Static-parse tests assert the header exists and matches the runtime sentinel set known to lib/halt.sh.

#!/usr/bin/env bash
# PHASE: preflight
# INPUTS:
#   PROJECT (env var, absolute path) — main repo path
#   PLAN_FILE (env var, absolute path) — plan path; may not exist for plan.sh
# OUTPUTS:
#   .autopilot-halt (sentinel, in $PROJECT) — written if preflight halts
# EXIT CODES:
#   0 — phase passed, autopilot may proceed
#   2 — halt-with-reason; .autopilot-halt has structured details
#   3 — skip (preflight not applicable)

set -u
source "$(dirname "$0")/../lib/process.sh"
source "$(dirname "$0")/../lib/halt.sh"
source "$(dirname "$0")/../lib/manifest.sh"
set -u everywhere Decision 7 explicit: autopilot.sh, run-ralph.sh, all phase scripts, and lib all use set -u only. Sourced libs inheriting different flag sets from different callers was a real trap; pinned now.

Mid-Flow Human Review (BANNED by writing-plans contract)

The proposition The autopilot's whole value is unattended completion from design doc to verified branch. The user reviews ONCE, at the end, after verify.sh halts cleanly or autopilot completes. Any plan task that inserts "human review" mid-pipeline defeats this proposition — even when framed as "verification," "confirmation," or "user check."

Distinct from the existing Manual Steps Policy in writing-plans/SKILL.md:100-111:

Manual Steps Policy

Governs execution the user must perform: env setup, OAuth, prod migrations.

+ Goes in Prerequisites or Post-Automation

+ Already enforced by Verifier critic

Halt-with-reason

Environment failures the executor genuinely cannot resolve. Halts cleanly, surfaces fix-instructions.

+ Phase exits 2; autopilot.sh exits 0

+ Halts are not failures

Mid-flow human review (BANNED)

Plan author wanted the user to provide judgment mid-flow. Pure ceremony.

— Defeats unattended completion

— Slips past existing policy

Banned task patterns

writing-plans MUST NOT produce plan tasks containing language like:

PatternWhy it's banned
"Get user feedback on X before proceeding"Pipeline doesn't pause for feedback
"Have the user verify the UI looks correct"Mockup fidelity loop is the machine check; user reviews at end
"Pause and ask if X is acceptable"No human present to ask
"Review the interface before continuing to Task N+1"User reviews when autopilot completes
"Confirm with user before proceeding"No conversational surface; loop will halt or guess
"Show user the [output/screenshot/result] and wait"Headless claude -p cannot wait for human input
"User signs off on the design before implementation"Sign-off happened during brainstorming; not a plan task
The pattern "Task body asks for judgment mid-pipeline." NOT "task body runs a machine check" — those are fine (mockup fidelity, eval scoring, verify gate are all machine-judged).

What's allowed

  • Prerequisites (before Task 1) — work the user does to unblock autopilot.
  • Manual Steps (Post-Automation) — work the user does after autopilot completes.
  • Halt-with-reason (.autopilot-halt) — environment failures the executor genuinely cannot resolve.
  • Mockup fidelity loop — machine check (claude compares implementation to mockup), not human review.
  • Verify gate — machine check (tests, build, eval), not human review.
  • End-of-autopilot review — the user reviews everything at the end, when the branch is ready.

Enforcement

The Verifier critic in references/critique-panel-prompts.md Criterion 10 (Autonomy violations) gains an explicit rule:

New Verifier rule Any task whose body contains "human review," "user verifies," "review the [UI/interface/mockup/output]," "wait for user," "confirm with user," "before proceeding ask," "user signs off," "get user approval," or semantically equivalent language MUST be flagged as HIGH severity. Suggest restructure: move to Manual Steps (Post-Automation) if it's real verification work, or remove if it's a gratuitous gate.

Exemption: Prerequisites, Manual Steps (Post-Automation), and Decision Log sections — these are explicitly user-facing and not part of the autopilot's task flow. Task bodies are not exempt regardless of where in the plan they sit.

The halt sentinel

A new .autopilot-halt sentinel mirrors the existing .ralph-human-blocked (per docs/plans/completed/2026-04-28-ralph-autonomy-enforcement.md Decision 2). Written by lib/halt.sh from any phase.

reason: mcp_tool_not_allowlisted
phase: preflight
fix-instructions: |
  The plan declared `mcp__playwright__browser_resize` but it is not in
  this project's `.claude/settings.local.json` allowlist.

  Fix one of:
    1. Open a Claude session in this repo and accept the permission prompt
       once: this writes the tool to the allowlist.
    2. Remove `mcp__playwright__browser_resize` from the plan's
       `mcp-tools-required` and from any task body that references it.

  Then re-run autopilot.sh.
Write protocol Atomic via mv $TMP $PROJECT/.autopilot-halt. First writer wins; subsequent writers append a secondary-halt: block rather than overwriting. Never auto-deleted by the orchestrator on retry — preserving evidence beats auto-cleanup.

Sequencing

  • Epic A ships first. No dependencies. Smallest delta. Cleans up bloat without changing behavior.
  • Epic D can ship parallel to A. Pure writing-plans contract change; doesn't touch the autopilot scripts.
  • Epic B depends on Epic A's phases/ decomposition and on Epic D's anti-review check (manifest authoring lives next to anti-review).
  • Epic C depends on Epic A's lib/ extraction but can ship in parallel with B and D.
  • Don't stop at Epic A. The recurring failure classes resolve only once B (MCP/env) and D (mid-flow review) are live.
