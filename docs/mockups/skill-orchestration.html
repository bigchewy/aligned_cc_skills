Mode Detection and RoutingRouter

Every brainstorming session starts here. The router classifies the topic, dispatches a background project scan, presents a mode explanation block, then hands off to the appropriate mode file.

  • Software mode signals: features, APIs, architecture, code, testing, data models
  • Business mode signals: strategy, sales, positioning, pricing, decisions, stakeholders
  • Tiebreaker: environment — code repo suggests software, docs-only repo suggests business
  • Project Scanner: dispatched immediately via Task tool in the background — does not block Q&A
  • Mode explanation block: always shown before phase work begins, names the mode and why it was selected

Software Mode OrchestrationSoftware

Software mode runs a fluid Q&A with automatic Architect consultation on technical decisions. Business questions go to the user; technical questions are auto-resolved via a fresh Architect sub-agent each time.

  • Business questions: asked directly to the user — product direction, scope, UX preferences, priorities
  • Technical questions: routed to The Architect via Task tool (model=opus) — data models, module boundaries, state, API shape
  • Architect as proxy: in Q&A phase, Architect makes decisions; in review mode (presenting options/design sections), it critiques only
  • UI options: Steve Krug may also be consulted for UX/usability decisions; mockup-generator dispatched for comparison mockups
  • Scan gate: Architect is not dispatched until project-scanner has completed and its output has been reviewed

Business Mode OrchestrationBusiness

Business mode is strictly sequential with phase gates. A complexity assessment after goal confirmation determines whether to run the full diagnostic sequence or streamline for tactical tasks.

  • Phase 1 — Goal: confirm a single clear goal sentence before proceeding
  • Complexity gate: operational (concrete checklist) streamlines Phase 2 and skips root causes; diagnostic (unclear why) runs full 4-phase sequence
  • Phase 2 — Problems: identify obstacles categorized as knowledge gaps, resource constraints, misalignment, complexity, execution gaps
  • Phase 3 — Root causes: 3-5 levels of "why" per obstacle; skipped for operational tasks
  • Phase 4 — Solutions: 2-3 approaches addressing root causes; proposal is locked until Phase 3 gate is confirmed
  • After design: hands off to After Design, then to business-write-plan

Post-Design Dispatch (Both Modes)After Design

After the design is written, both modes follow the same pattern: write design doc, dispatch session-document-generator for visualization, run the critique panel, then commit everything.

  • Design doc: written to docs/plans/YYYY-MM-DD-topic-design.md
  • session-document-generator: dispatched via Task tool — reads design doc, dispatches flowchart/architecture/mockup sub-agents in fragment mode, assembles tabbed HTML, runs Mermaid verification
  • Critic panel: dispatched in parallel (software: division-of-labor with one fact-checker; business: all critics fact-check independently)
  • Visualization refresh: re-dispatched if the design doc changed after critique corrections
  • Software next steps: Autopilot or Hands-on path
  • Business next steps: business-write-plan → business-executing

Autopilot PhasesPipeline

autopilot.sh orchestrates five sequential phases from design doc to verified branch. You walk away after launching it. Each phase writes a sentinel file so the script can resume after interruption.

  • Phase 1 — Plan writing: invokes claude -p with WRITE-PLAN.md prompt (runs the full writing-plans workflow including 2-critic panel); writes plan path to sentinel file
  • Phase 2 — Worktree: creates feature branch + worktree, installs deps, links .env files, merges main so the plan is accessible
  • Phase 3 — Ralph loop: delegates to run-ralph.sh; each iteration is a separate claude -p instance executing one task. See Ralph Loop for details.
  • Phase 3.5 — Mockup fidelity: iterative loop (up to 5x) comparing implementation against HTML mockups; writes .mockup-clean when clean
  • Phase 4 — Verify: runs VERIFY-BRANCH.md prompt (tests, build, eval); writes .finish-status with SUCCESS or FAILED

ResumabilityResilience

Safe to re-run after interruption. Each phase checks for its completion artifact before executing; completed phases are skipped automatically.

  • .autopilot-plan-path: two-line sentinel (design doc path + plan path) — Phase 1 skipped if present and plan file exists
  • Worktree directory: Phase 2 checks existence; if found, creation is skipped but merge-main still runs
  • ✅ markers in plan: the Ralph loop picks up from the first unchecked task — completed tasks are never re-run
  • .mockup-clean: Phase 3.5 skipped if this file exists in the worktree
  • .finish-status: Phase 4 skipped if status: SUCCESS; cleared and re-run if status: FAILED

Ralph Loop — One Task Per Claude InstanceLoop

run-ralph.sh spawns a fresh claude -p process per iteration, each executing exactly one plan task. Progress is preserved via ✅ markers in the plan file; the loop exits when .ralph-done is written. Also available standalone outside autopilot — see Hands-On Path.

  • One task per instance: each Claude invocation reads the next unchecked task heading, executes it, marks it ✅, commits, then exits
  • Sentinel file: when all tasks are ✅, the instance writes .ralph-done and exits; the shell loop detects this and breaks
  • Timeout watchdog: each iteration has a 15-minute SIGKILL watchdog; 5 consecutive timeouts abort the loop
  • Consecutive failure cap: 3 consecutive non-zero exit codes abort the loop

Writing Plans — Research and CritiquePlan

The writing-plans skill explores the codebase, writes a detailed plan with verified file paths, then runs a 2-critic panel in parallel before committing the plan to main.

  • Codebase research: reads architecture.md, uses Glob/Grep/Read (or Explore sub-agent for heavy research) to verify every file path before writing
  • Plan location: always written to the main worktree's docs/plans/ and committed to main — survives branch discard
  • Round 1 critics (parallel): The Architect (codebase alignment, module boundaries, gap analysis) and The Verifier (every claim verified against source, design fidelity, mockup coverage)
  • Aggregation sub-agent: merges both reports into a single actionable summary under 1500 words
  • Round 2 (conditional): only if medium/high issues found; scoped to changed sections only; uses haiku model
  • After plan: presents execution options — interactive or Ralph loop, or autopilot (skips Phase 1 since plan already exists)

Executing Plans — Autonomous Batch CycleExecute

executing-plans loads the plan from main, verifies it's on a feature branch, and executes all tasks autonomously without pausing. It only stops on blockers or verification failures. Alternatively, use run-ralph.sh for fresh context per task.

  • Branch guard: refuses to run on main/master — requires a feature worktree
  • Plan from main: reads plan via git worktree list to find the main worktree path
  • Autonomous mode: executes all tasks without pausing for review — only stops on blockers or failed verification
  • LLM surface check: if a task touched advisor prompts or prompt builders, runs evals immediately
  • Bug board: out-of-scope bugs discovered during execution are logged to docs/kanban/todo/
  • Archive: on completion, plan + design doc moved to docs/plans/completed/ on main
  • After execution: run finishing-a-development-branch in a new session from the main repo

Finishing a Development BranchFinish

Always runs from the main repo, never inside a worktree. Applies after both autopilot and hands-on paths. Runs a sequential checklist before presenting options.

  • Deployment audit: scans for Vercel pitfalls (file system access, dynamic requires, module-level mutable state, native deps) — CRITICAL findings block merge
  • Test + build gate: both must pass before proceeding
  • LLM eval: auto-runs if any files matching LLM behavior surface patterns were changed on the branch
  • Architecture doc: updates docs/architecture.md if structure-relevant files changed
  • Code simplifier: read-only sub-agent scans branch diff for simplification opportunities; filed to Kanban board (non-blocking)
  • Mockup fidelity: compares implementation against HTML mockups; unannounced deviations trigger root-cause diagnosis loop (up to 5 cycles)
  • 4 options: merge locally, deploy + smoke test (Vercel MCP or wait + check), keep as-is, discard (with confirmation)
  • Cleanup: removes worktree, archives plan docs to docs/plans/completed/
