Contextual Recommendation

Intent-based advisor and framework selection from YAML registries

When use-advisor or use-framework is invoked without a specific name, recommend the best match from the registry based on task context. Two-stage scoring (LLM-assisted domain filter, then semantic ranking) with confidence-gated presentation: auto-select when unambiguous, shortlist when signals are mixed. Unprofiled advisors are excluded from scoring. Shared scoring logic in a single file consumed by both skills.

Four-Path Invocation Cascade decision flow

Every invocation enters a four-step cascade evaluated in order. The first match wins. Named matches short-circuit before scoring runs. Contextual paths extract task signals from args or conversation. Bare invocations with no signal prompt the user.

Cascade Decision Flow 4 paths

Invocation enters at the top. Each diamond is an evaluated condition. First match wins and routes to the corresponding action.

  • Path 1 (Named): Args match a slug or display name — existing behavior, no scoring
  • Path 2 (Args context): Args present but no name match — treat as task context, run scoring
  • Path 3 (Conversation context): No args, but conversation has task signals — extract and score
  • Path 4 (Prompt): No args, no conversation context — ask the user what they need

Path-by-Path Breakdown behavior

Each path has distinct input conditions and output behavior. Named matches preserve existing behavior. Contextual paths are the new capability.

PathInput ConditionActionOutput
1 — Named Args match a slug or display name (case-insensitive substring) Short-circuit, no scoring Adopt advisor / run framework
2 — Args context Args present, no name match Treat args as task context, run two-stage scoring Auto-select or shortlist
3 — Conversation No args, conversation describes a task/project/domain Extract context from conversation, run scoring Auto-select or shortlist
4 — Prompt No args, conversation is empty/generic/unrelated Ask user what they are working on User input or "list all" escape

Path 3/4 Boundary Examples calibration

The LLM judges whether the conversation contains "useful context." These examples calibrate that judgment. If recent messages describe a task, project, or problem domain, use Path 3. If the conversation is empty, generic, or unrelated to advisory/framework work, use Path 4.

Cascade Decisions D2, D3, D4

Architect-validated decisions that shaped the invocation cascade design.

#DecisionRationale
D2 Name-first cascade, no detection heuristic Try name matching first (deterministic). If no match, args are task context by elimination. Avoids impossible classification of ambiguous inputs like "marketing."
D3 Use conversation context when no args provided The LLM already has the full conversation when the skill fires. Instruction-only change, no infrastructure.
D4 Prompt for context on true bare invocations Better than dumping a raw list. "What problem are you working on?" with "list all" escape hatch.

Two-Stage Scoring Flow core algorithm

LLM-assisted domain pre-filter narrows the candidate set, then semantic ranking applies natural language priority rules. Unprofiled advisors are excluded before scoring. Candidates are shuffled to mitigate position bias. A structural confidence test determines whether to auto-select or show a shortlist.

End-to-End Scoring Pipeline flow

Task context enters from the left. Unprofiled entries are excluded first. LLM-assisted domain filter reduces 65 advisors / 139 frameworks to ~5-20 candidates. Candidates are shuffled before semantic ranking to mitigate position bias. Confidence test gates the output mode.

  • Eligibility filter excludes unprofiled advisors (no best_for/not_for) — they remain accessible via named invocation
  • Domain filter uses LLM-assisted keyword extraction: the LLM maps natural language to domain tags, then matches against registry tag lists
  • Candidate shuffling presents filtered candidates in random order, not registry order, to eliminate position bias
  • Semantic ranking runs LLM natural language priority rules on the shuffled candidate set only
  • Confidence test is structural: can the LLM articulate why the top pick wins and the runner-up doesn't?
  • Zero-candidates fallback: If Stage 1 produces no matches, skip it and run full-registry Stage 2

Stage 1: Domain Filter LLM-assisted keyword extraction

Extract domain signals from the user's task context — the LLM maps natural language input (e.g., "I need a landing page") to domain tags (e.g., [landing-pages, conversion-optimization]). Then match extracted tags against each registry entry's domains tag list. Any entry sharing at least one domain tag passes to Stage 2.

  • Extraction step: LLM-assisted — maps prose to domain tags constrained to the vocabulary of existing domains tags in the registry
  • Matching step: Straightforward tag overlap, not full semantic inference
  • Scoring eligibility: Entries with domains: [] (empty tag list) are invisible to Stage 1 — unprofiled advisors with empty domains are naturally excluded
  • Expected reduction: ~30 profiled advisors to ~5-10 candidates, 139 frameworks to ~10-20
  • Position bias mitigation: Candidates are shuffled before passing to Stage 2
  • Zero overlap: Entry excluded from Stage 2

Stage 2: Semantic Ranking LLM, 4 priority rules

Applied to the shuffled, filtered candidate set only. Four priority rules evaluated in order. Natural language matching plays to LLM strengths — no numeric weights on prose fields.

  • Rule 1 — Hard exclusion: Remove entries whose exclusion field matches the task's primary domain
  • Rule 2 — Primary match: Semantic comparison of task against each entry's inclusion field (strongest signal)
  • Rule 3 — Domain depth: More domain tag overlap ranks higher (tiebreaker only)
  • Rule 4 — Disambiguation: Finer-grained fields for remaining ties

Structural Confidence Test D7

Not a numeric score. The LLM must be able to articulate why the top pick matches and why the runner-up doesn't match as well. If it can't articulate the gap, it's not confident — shortlist instead.

  • High confidence: Top entry's primary match field clearly describes the user's task, runner-up is noticeably less relevant
  • Low confidence: Two or more entries are plausibly relevant, or best match is only tangential
  • Bias: Explicitly toward shortlisting — auto-select is reserved for unambiguous matches

Debuggability and Upgrade Path D6

Natural language scoring is not auditable the way numeric scoring is. Recommendations may vary across invocations for the same input. This section documents the trade-off and the upgrade path.

  • v1 trade-off: The LLM's semantic matching strength outweighs the consistency loss at this scale. Acceptable for launch.
  • Variability: Same input may produce different recommendations across invocations. The shuffling step adds further non-determinism (by design — it prevents systematic position bias).
  • Upgrade path: If recommendation stability becomes a user-reported issue, a precomputed index approach (matching the auto-router's skill-router.json pattern) is the next step. This would replace LLM-time scoring with pre-indexed embeddings or keyword maps.
  • What doesn't change: The two-stage architecture (filter then rank) and the structural confidence test remain valid under either approach.

UX Modes D8

Two presentation modes determined by the structural confidence test. Auto-select proceeds immediately for fast workflows. Shortlist preserves user agency when signals are mixed. Both include a "list all" escape hatch.

Auto-Select Mode high confidence

One entry clearly matches. The skill proceeds immediately with the selection — no confirmation gate. To switch, the user re-invokes the skill with a different name. Mirrors brainstorming mode selection pattern.

  • Trigger: Top entry's primary match field clearly describes the task, runner-up is noticeably less relevant
  • Behavior: Skill immediately adopts advisor persona or begins framework Phase 1
  • Override: Re-invoke the skill with a different name (e.g., /aligned:use-advisor april-dunford), or say "list all"
Auto-select presentation
Selected: Oli Gardner — Landing page optimization is his primary expertise, and your task is specifically about building a landing page.
Alternatives:
• Seth Godin — Broader marketing strategy, less focused on landing pages specifically
• Donald Miller — StoryBrand messaging could apply, but not landing-page-specific
To switch, re-invoke the skill with a different name. Or say "list all" to browse the full catalog.

Shortlist Mode low confidence

Multiple entries are plausibly relevant, or the best match is only tangential. No auto-selection — the user chooses.

  • Trigger: Two or more entries are plausibly relevant, or the LLM can't articulate a clear gap
  • Behavior: Show 2-3 entries with rationale, wait for user choice
  • Escape: "list all" to browse the full catalog
Shortlist presentation
Based on your context, these look relevant:
1. Robbie Baxter — Membership and subscription pricing models
2. April Dunford — Positioning-driven pricing strategy
3. Patrick Campbell — Data-driven SaaS pricing optimization
Which would you like to use? Or say "list all" to browse the full catalog.

Prompt for Context Path 4

True bare invocation with no args and no useful conversation context. Better than dumping a raw list of 65+ entries.

  • Trigger: No args, conversation is empty, generic, or unrelated
  • Behavior: Ask the user what they are working on
  • Escape: User can say "list all" to browse the full catalog
Prompt presentation
What problem are you working on, or what are you trying to accomplish? I'll recommend the best fit.

Implementation Order 4 phases
