Project Scanner Agentnew agent

A self-contained sub-agent dispatched via the Task tool. Receives a project root and topic slug, scans the project structure, and writes findings to /tmp/. Both skills use the identical dispatch pattern. The scanner adapts its investigation based on what it finds: code-heavy projects get tech stack analysis, document-heavy projects get domain material emphasis.

  • Input: project root path + topic slug
  • Output: writes to /tmp/brainstorm-context-{topic}/project-scan.md, returns summary under 300 words
  • Tools: Bash (git only), Glob, Grep, Read, Write
  • Model: opus (frontmatter setting)
  • New for business: scan findings help Claude ask better questions during goal clarification and problem diagnosis

Shared Critique Panel Orchestrationnew shared file

The shared file at skills/_shared/critique-panel-orchestration.md contains the full critique workflow. Each calling SKILL.md sets configuration parameters before reading it, making the same orchestration logic serve both fact-check modes and aggregation strategies. A configuration validation preamble catches misconfigured parameters before execution.

  • Config validation preamble: verifies all required parameters are present before proceeding; STOPs with a clear error if any are missing from the SKILL.md configuration block
  • Mandatory sub-agent rule: all critique rounds run as fresh sub-agents via Task tool, never in main context
  • Checklist resolution: inlined (not a separate shared file) to keep reference depth at one hop from SKILL.md
  • Two fact-check modes: division-of-labor (technical) and all-critics (business)
  • Apply-fixes-before-Round-2: incorrect facts are corrected and user-approved critique fixes are applied before Round 2 critics see the document

Why All-Critics for BusinessD4 rationale

The business skill uses all-critics fact-checking instead of division-of-labor. This is not a preference toggle but reflects fundamentally different checklist semantics.

  • Different search strategies: business fact-checking uses WebSearch/WebFetch where different critics bring different search strategies for the same claim
  • Token waste argument doesn't apply: in technical, codebase fact-checking is deterministic (duplicate work is wasted); in business, multiple perspectives on the same claim have value
  • Criteria don't map: criteria-assignment: no is structurally required because the business checklist has entirely different criteria (goal precision, root cause depth, stakeholder mapping) that don't map to the same domain buckets

Decision Detailsrationale

#DecisionRationale
D1Use _shared/*.md "read this file" patternAlready established by 6+ skills. No build step, no preprocessing. Note: the shared critique panel is a new category (parameterized orchestration protocol, ~60 lines, 7 parameters) vs. simple reference docs. Config validation preamble mitigates misconfiguration risk.
D2Extract project scan to agents/project-scanner.mdSelf-contained unit of work matching the agent pattern. Receives project root + topic, writes findings to /tmp/, returns summary.
D3Inline checklist resolution into critique panel fileOne-hop max from SKILL.md. Shared file referencing another shared file creates two hops. The kanban-entry-format precedent is always a leaf node.
D4Keep business brainstorming on all-critics fact-checkBusiness uses WebSearch where different critics bring different search strategies. criteria-assignment: no is structurally required — different checklist semantics, not a preference toggle.
D5Upgrade business to sub-agent aggregationInline aggregation consumes main-thread context with raw reports. Sub-agent keeps reports in /tmp/ and returns concise summary. Acknowledged as a new capability, not pure extraction.
D6Add visualization to business brainstormingsession-document-generator has a global fallback for design-principles at ~/.claude/docs/design/design-principles.md, so it will not hard-fail on business projects. Business benefits from process flow, decision flow, and data flow diagrams. Conditional dispatch: only if design warrants visuals.
D7Selective sync modelSome improvements cross over (orchestration, project scan, visualization), others don't. Architect consult is technical-only; 4-phase is business-only.

Testing Strategyverification

Four layers of verification ensure the refactor preserves behavior while achieving the structural goal and new capabilities. Structural checks run first (automatable), followed by validation, manual smoke tests, and regression checks.

  • Structural verification: both SKILL.md files reference shared modules, no orphaned inline critique panels remain, no two-hop references, project-scanner.md has model: opus frontmatter
  • Structural validation: grep both SKILL.md files for shared file references, verify business-brainstorming references session-document-generator, verify config blocks contain all required parameters
  • Manual smoke tests: run each skill with a small topic, verify agent dispatch, critique mode, shared file reading, and new business visualization
  • Regression checks: next-step prompts, standalone design critique mode, untouched sections all still functional
  • Shared file regression rule: changes to _shared/critique-panel-orchestration.md MUST be smoke-tested against both skills (only 2 consumers, so testing both is feasible and required)
