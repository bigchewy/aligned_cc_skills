The AI-Native Brand Folder

A canonical shape for digital health companies becoming AI-native — where generator agents consume brand context to produce decks, blog posts, one-pagers, emails, landing pages, and battlecards. Same shape, different fills across digital-health subdomains.

Date 2026-05-15 Topic ai-native-brand-folder Mode Authoring Revision v0.5 Target: digital health companies

01Why now

Three forces collide, and waiting compounds the cost.

Generators are multiplying

Ten or more generator agents will reach into brand/ within the next year. Today they hardcode paths; they break the moment an org's folder diverges.

Two prior-art instances disagree

dispatch-tracker/brand/ and planted/brand/aligned/ started from the same intent but drifted. No canonical scaffold exists for a new B2B org.

Reverse-engineered-brand needs a target

The bootstrap framework that turns a public URL + local content folder into a draft brand folder can't ship without a defined target shape.

The goal is not to redesign what dispatch-tracker has — most of it is correct. The goal is to name what each slice owns, kill duplication, add AI-native infrastructure (frontmatter contract, provenance, slice-loading, composition contract), and stamp the result as canonical so every existing generator and every future generator share one source of truth.

02Goal

Define the canonical brand/ folder that an AI-native digital health company installs once, and from which every brand-consuming skill — generators, audits, persona checks, battle-card builders — reads predictably.

  • Work uniformly across digital-health subdomains (telehealth, RPM, behavioral health, digital therapeutics, payer-side, provider-side, condition-specific platforms).
  • Be machine-loadable in slices so generators pull only what they need.
  • Encode provenance so an agent can reason about which content is validated vs draft — with a higher bar in digital health, where claims often need clinical-evidence backing.
  • Ship with a manifest that tells the next thread what to deepen next.

03Hard constraints

Single-org per repo. Top-level brand/, single-tenant. No nested brand/{slug}/ patterns. Multi-brand orgs use separate repos.
One shape, every digital health company. Directory layout identical across subdomains — telehealth, RPM, behavioral health, digital therapeutics, payer-side, provider-side, condition platforms. B2C consumer wellness, general B2B SaaS, agencies, and advisory practices are out of scope as target users. dispatch-tracker/brand/ is retained as a structural reference instance only.
AI-first design. Primary consumer is generator agents (~95% of reads). Humans validate occasionally. Optimize for machine-parseable structure, terse summaries, dense slice tagging.
Frontmatter mandatory on every .md. No bare markdown.
No content duplication. A claim lives in exactly one file. Other files reference it by slice path.
Provenance encoded structurally. Three states only: status: draft | validated | retired.
Confidence as label. confidence: low | medium | high. No numeric scores.
Slice-loadable by H2. {file}#{slug}. No nested H2-as-decoration.
CLAUDE.md is the front door. Lists every file, every slice, every consumer, and the "deepen next" queue.
No symlinks outside the repo. Source-of-truth lives in brand/.
One loader, not six. v1 ships shared skills/_shared/load-brand-slices.md. Generators delegate.
Clean-state cutover. No legacy-paths.yaml. Existing generators update to new paths in the same change. No deprecation window.
Brand is durable; clients/ is transient. Per-deal prospect context lives in a sibling clients/{prospect-name}.md, NOT in brand/.
Templates are org-customized. brand/templates/{type}/ holds the org's specific output structure. Generators stitch org template + org content + prospect file.

04Core commitments

Structural orthogonality — Dunford-validated boundary

Three strategic files, three jobs:

  • strategy/positioning.md — "if it requires reasoning to defend, it's positioning" — the 5-component chain. Internal-facing thesis. Changes ~2× per year.
  • language/messaging.md — "if it's a string you'd paste into a slide, it's messaging" — category name, tagline, elevator variants, value-prop-to-persona map. Changes constantly.
  • strategy/narrative.md — "if it's an arc, not a logic chain, it's narrative" — Raskin's 5-element story shape. Changes when strategy shifts.

Three change cadences = three files = three review processes. Fusing any two couples change rates that should stay independent.

Markets vs roles

audiences/ = markets (verticals). personas/ = roles. They compose at generation time.

Brand voice ≠ person voice

voice.md is institutional. voices/{name}.md (optional) for named spokespeople.

Slices over files

A generator that needs the category name loads messaging#category-name, not all of positioning.md.

Confidence as label

Every file declares confidence: low | medium | high. Generators consume thresholds.

Manifest tells you what's next

CLAUDE.md ends with "Next Steps to Deepen This Brand Folder" — a framework queue.

Templates are per-org

Each org's brand/templates/ holds its own deck/blog/email structure. Generators stitch.

06Frontmatter schema

Mandatory on every .md. Seven required + a handful of optionals. AI-first: terse summaries, dense slice tagging.

---
id: guideline-positioning
type: positioning                          # positioning|narrative|messaging|voice|persona|audience|...
slices:
  - competitive-alternatives
  - unique-attributes
  - value
  - target-customers
  - category
status: draft                                # draft | validated | retired
confidence: medium                          # low | medium | high
updated: 2026-05-15
validated_at: 2026-05-15                   # OPTIONAL
validated_by: eric.w.page@gmail.com          # OPTIONAL
sources:                                    # OPTIONAL — typed citations
  - { kind: url, value: "https://dispatchtrack.com" }
depends_on:                                 # OPTIONAL — slice graph edges
  - "strategy/positioning#category"
consumers: [generate-deck]
tags: [positioning, dunford]
summary: > 5-component positioning chain.
---

07Provenance & confidence

StatusMeaningGenerator behavior
draftGenerated/inferred; no human sign-offUse, include "DRAFT" disclaimer in output appendix
validatedReviewed and approvedUse without disclaimer
retiredSuperseded; preserved for contextSkip entirely

Confidence labels

LabelMeaningThreshold behavior
highPrimary source — quote, interview, audited metric, founder-validatedUse freely
mediumStrong inference or corroborated secondary sourceUse; flag if min_confidence=high
lowSpeculative, pattern-matched, or stubExclude unless explicitly opted in

Generators MAY accept a min_confidence parameter (low | medium | high, default medium). Per-section override pragma available when one section diverges from file-level: > [PROVENANCE: status=draft, confidence=low, source=website-inference].

08Slice-loading mechanics

Every H2 is a slice. {folder}/{file-stem}#{slice-slug}. Lowercase, replace non-alphanumerics with -, collapse repeats.

CaseRule
Two H2s slug-collideAppend -2, -3 in document order. Lint warns.
slices: declares a slug missing from bodyLoader returns status: missing-in-body. Lint fails.
H2 in body, not in slices:Loader does NOT expose. Lint warns.
Non-markdown files (CSS, images, fonts)Exempt from frontmatter. Manifest shows status: n/a.

v1 ships one loader at skills/_shared/load-brand-slices.md. Every generator delegates — no inline frontmatter parsing.

10Composition contract

Lives at brand/contracts.yaml. Source of truth for which generator reads what. Generators also load clients/{prospect}.md as a third overlay.

generators:
  generate-deck:
    requires:
      - strategy/positioning
      - language/messaging#category-name
      - language/messaging#value-prop-phrasings
      - language/messaging#value-prop-to-persona-map
      - language/voice#tone-principles
      - personas/{role}           # from clients/{prospect}.md
      - audiences/{vertical}      # from clients/{prospect}.md
    optional:
      - strategy/narrative
      - proof/proof-points
      - market/competitive
    compose:
      brand_x_clients: "load brand slices, then clients/{prospect}.md as third overlay"
      persona_x_audience: "base=persona, overlay=audience (last-write-wins per H2)"
    min_confidence: medium

  # ... generate-blog-post, generate-one-pager, generate-email,
  #     generate-landing-page, generate-battlecard, plus 4+ future generators

# Forward-compat — third-party plugin SKILL.md brand_contract blocks merged at runtime
extends: []

17Migration & adoption

Clean-state cutover. No aliasing shim. Single coordinated PR migrates the dispatch-tracker reference instance and updates the existing generator skills in the same change.

Single-PR migration

  1. Backfill dispatch-tracker/brand/ — one-shot script:
    • Add the new required frontmatter fields with defaults; generate slices: from existing H2s.
    • Move files to layered homes: guidelines/positioning.md → strategy/positioning.md, guidelines/brand-voice.md → language/voice.md, etc.
    • Split guidelines/messaging-framework.md per Dunford boundary: reasoning content folds into strategy/positioning.md; copy-ready strings move to language/messaging.md.
    • Write version.yaml starting at 0.4.0.
    • Ship contracts.yaml.
  2. Update generator skills in the same PR. ~/.claude/skills/generate-{deck,blog-post,one-pager}/SKILL.md get path updates OR delegate to the shared loader (preferred).
  3. Lint enabled from day one. Frontmatter required-field lint fails the build on missing fields. No warning-only grace period.

No deprecation window. No aliases. The cost is a coordinated change; the benefit is a clean v1 with no shim to remove later.
