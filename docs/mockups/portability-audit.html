Portability Audit

Skill design for /aligned:portability-audit

Scans the Aligned plugin repo for environment-specific hardcoding (absolute user paths, external file dependencies, platform assumptions) that would break the plugin for other users. Single-pass skill with reference catalog, 3 detection categories, and severity-grouped reporting.

End-to-End Flow

The portability audit runs as a single-pass skill: gather context, discover files, scan patterns, filter false positives, and generate a severity-grouped report. Three detection categories across three severity levels.

Architecture Decisions 5 decisions

Key design choices and their rationale. The skill follows the single-pass pattern from finishing-a-development-branch Step 0 and the reference catalog pattern from deployment-pitfall-catalog.md.

DecisionChoiceRationale
Execution model Single-pass SKILL.md with reference catalog All 3 categories use the same method (Grep + filter). No analytical diversity that benefits from parallel sub-agents.
False-positive handling Inline rules in reference catalog Only 6 stable categories of safe patterns. An external allowlist would be scanner logic with extra steps.
File discovery git ls-files via Bash Git-aware filtering is a git concept. Glob cannot respect .gitignore rules.
Output format Severity-grouped findings Matches deployment audit report format. No confidence scores, no dimension tables.
Scope This plugin repo only Not designed as a general-purpose portability scanner for arbitrary repos.

Skill Structure 2 files

Self-contained skill with no agents, no workers, no sub-agent dispatching. Detection knowledge lives in the reference catalog; the SKILL.md orchestrates scanning.

  • SKILL.md — Entry point with frontmatter, scanning process orchestration

P1: Absolute User Paths CRITICAL

Paths containing a literal username directory. Always breaks on another machine, no ambiguity. This category subsumes hardcoded home directory values (e.g., /Users/ericpage/.config/... instead of $HOME/.config/...) since the same regex catches both patterns.

  • Detection: Grep for patterns matching /Users/<name>/, /home/<name>/, C:\Users\<name>\
  • Regex: /Users/[a-zA-Z][a-zA-Z0-9._-]+/ and equivalents for Linux/Windows
  • Severity: CRITICAL — always breaks on another machine
  • Fix: Replace with ~/.claude/, $HOME, or {base-directory}

P2: Non-Plugin External File Dependencies HIGH

References to files outside the plugin tree that are not standard Claude Code paths. The skill will fail for other users if the file does not exist and there is no fallback. Paths containing template variables ({base-directory}, {project-root}, etc.) are skipped.

  • Detection: Paths containing ~/ followed by directories that are not .claude/ or .config/, AND the referenced file does not exist in the plugin repo
  • Severity: HIGH — skill fails for other users if no fallback
  • Note: References with fallback chains (local → global → plugin default) are handled by false-positive rules
  • Fix: Add fallback chain: check local repo first, then ~/.claude/, then plugin-bundled default

P3: Platform-Specific Assumptions MEDIUM

macOS-only commands or paths that break on Linux but not on other macOS machines. Only flagged in executable files, not documentation.

  • Detection: macOS-only commands like date -j, pbcopy, open (without fallback), or /usr/local/bin/
  • Scope: Only in executable files (.sh, .js) — not in documentation describing macOS usage
  • Severity: MEDIUM — breaks on Linux but not on other macOS machines
  • Fix: Add cross-platform fallback using || or command -v feature detection

Portable Home Directory References P1, P2

These path patterns expand per-user at runtime and are standard conventions. They are always safe.

  • ~/.claude/ paths — Tilde expands per-user, standard Claude Code convention
  • ~/.config/ paths — XDG base directory convention
  • $HOME, ${HOME}, process.env.HOME, os.homedir() — Programmatic home directory resolution

Runtime-Resolved Placeholders P1, P2

Template variables resolved by Claude Code at skill load time. They never contain a literal user path.

  • {base-directory}, {project-root}, {plugin-root}, {design-file-path} — Template variables
  • ${CLAUDE_PLUGIN_ROOT} — Plugin runtime environment variable

Graceful Fallback Chains P2, P3

Mechanically detectable patterns only. No natural-language heuristics. Fallback chains expressed only in natural language (e.g., "If not found, read ~/.claude/Y") are NOT auto-suppressed — they are reported as findings for human review.

  • Shell || chaining on the same line (e.g., date -j ... || date -d ...) → SAFE
  • command -v feature detection (e.g., command -v gstdbuf || stdbuf) → SAFE
  • Shell conditionals (if [ -f ... ]; then ... else ...) → SAFE

Documentation References all categories

Paths used as examples in documentation are not real dependencies. Narrowed to two mechanically detectable patterns.

  • Fenced code blocks with generic placeholders → SAFE
  • Same-line e.g. marker — paths on the same line as an e.g. marker → SAFE (covers inline examples like ~/software/project-a)

CLAUDE.md Documented Conventions all categories

Phase 0 reads the repo's CLAUDE.md files. Any path pattern explicitly documented there as intentional is safe.

  • Scope: Main CLAUDE.md and any nested CLAUDE.md files in subdirectories
  • Application: Any path pattern called out as an intentional convention gets excluded from findings

Verify repo identity, then read project conventions and detection rules before scanning. This context is used in Phase 3 for false-positive filtering.

  • Read reference catalog — references/portability-pitfall-catalog.md for detection categories and false-positive rules

Phase 1: File Discovery Bash only

The only Bash commands in the skill. Combines tracked and untracked non-ignored files, filtered to scannable text extensions. If either git command fails, the skill stops — do not proceed with an incomplete file set.

  • git ls-files — All tracked files
  • git ls-files --others --exclude-standard — Untracked non-ignored files
  • Extension filter: .md, .json, .yaml, .yml, .sh, .js, .ts, .toml, .txt, .html
  • Error handling: If either git command fails (e.g., not a git repo), report the error and stop

Phase 2: Pattern Scanning core detection

For each detection category (P1-P3), run Grep across the file set with the category's detection regex. Collect matches with file path, line number, and 2 lines of surrounding context. If a Grep command fails for a category, report it as a scan error rather than silently skipping.

  • Tool: Grep with category-specific regex patterns
  • Context: 2 lines of surrounding context per match for false-positive evaluation
  • Scope: All 3 categories run sequentially against the same file set
  • Error handling: Per-category scan errors reported as "SCAN ERROR: [category] — [error]"

Phase 3: False-Positive Filtering 5 rules

Each match runs through cross-cutting rules first, then category-specific rules. Any rule marking a match as SAFE excludes it from the report.

  • Cross-cutting rules first: Portable home dir, runtime placeholders, fallback chains (mechanical only), documentation references, CLAUDE.md conventions
  • Then category-specific rules: Per-category exceptions defined in the reference catalog
  • Multi-line context: Use Read for rules needing more context (e.g., shell conditional fallback detection)

Phase 4: Report Generation output

Group surviving findings by severity (CRITICAL, HIGH, MEDIUM), then by category within each severity. Include a "Clean Categories" section for categories with zero findings.

  • Severity ordering: CRITICAL → HIGH → MEDIUM
  • Per finding: File path with line number, matched text, risk explanation, suggested fix
  • All-clean shortcut: "No portability violations found. The plugin is portable." — no verbose empty report

Report Format: With Findings example

When violations are found, the report groups them by severity with per-finding detail: file path, matched text, risk explanation, and suggested fix.

## Portability Audit Report Scanned: 87 files (85 tracked, 2 untracked) Findings: 2 total (1 critical, 1 high, 0 medium) ### CRITICAL #### P1: Absolute User Path - File: skills/some-skill/SKILL.md:42 - Match: /Users/ericpage/.claude/skills/ - Risk: Path contains literal username — fails on any other machine - Suggested fix: Replace with ~/.claude/skills/ or {base-directory} ### HIGH #### P2: Non-Plugin External File Dependency - File: agents/some-agent.md:28 - Match: ~/.claude/docs/design/design-principles.md - Risk: References file outside plugin tree with no fallback - Suggested fix: Add fallback chain ### MEDIUM (no findings) ### Clean Categories - P3: Platform-Specific Assumptions — no findings
