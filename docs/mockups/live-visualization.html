Live Visualization for Brainstorming

Design: Real-time browser visualization during brainstorming sessions

Agent writes a self-refreshing HTML file during brainstorming. Browser auto-reloads every 3 seconds. At session end, the refresh script is stripped and the file becomes the permanent artifact. No web server, no process management.

System Overviewarchitecture

The live visualization system has four components: a component reference file the agent reads once, the agent's write operations, the self-refreshing HTML in /tmp (session-isolated via timestamp), and the finalized artifact in docs/mockups/. Click any node to explore that topic.

Rollbacksafety net

If live visualization fails during a session: revert the mode file changes and restore the session-document-generator dispatch. This is a single git revert. The session-document-generator agent and all diagram sub-agents remain unchanged and functional throughout.

Future Expansion

If the file-based approach proves out, natural next steps include extending to other skills (framework walkthroughs, critique panels) and adding interaction capture. A persistent web server becomes justified only if users hit concrete UX problems with file-based refresh.

Data Flowflowchart

The data flow is linear and file-based. The agent writes HTML using the Write tool, the browser reloads on a 3-second timer, and the cycle repeats until the session ends. A pre-critique copy step ensures the critique panel reads from docs/mockups/ at its configured path. No server, no sockets, no IPC.

  • Read once: Agent reads skills/brainstorming/references/brainstorm-components.md at visualization start
  • Write to /tmp: Initial HTML written to /tmp/brainstorm-{topic}-{timestamp}/live.html (timestamp provides session isolation)
  • Auto-reload: Self-refresh script triggers location.reload() every 3 seconds (30-minute timeout)
  • Incremental updates: Agent overwrites the same file as each design section is validated
  • Pre-critique copy: Copy live file to docs/mockups/{session-name}.html so critique panel can access it
  • Post-critique: If design changed, fully regenerate at docs/mockups/; strip refresh script from final copy

Session Lifecycle3 phases

The lifecycle is fully automatic. The brainstorming skill triggers visualization at the design presentation phase. Updates happen during presentation. Finalization includes a pre-critique copy step and post-critique conditional regeneration. No user management required.

Phase 1 — Startautomatic

Triggered automatically at the design presentation phase. The agent reads the component reference, writes the initial HTML to a session-isolated /tmp path, and opens the browser. The self-refresh script starts a 3-second reload cycle with a 30-minute timeout.

  • Step 1: Agent reads skills/brainstorming/references/brainstorm-components.md (template + CSS component classes)
  • Step 2: Agent writes initial HTML to /tmp/brainstorm-{topic}-{timestamp}/live.html (timestamp prevents collision if the same topic is brainstormed twice)
  • Step 3: Agent opens the file using a platform-aware command: open /path on macOS, xdg-open /path on Linux (separate Bash calls — must not chain with &&). If the open command fails (headless environment), log a warning and continue.
  • Step 4: Browser opens, self-refresh script begins 3-second polling (with 30-minute timeout to prevent indefinite reload)

Phase 2 — Updateiterative

During design presentation, the agent presents each section in chat. After the user validates, the agent updates the HTML file. The browser picks up the change within 3 seconds on the next reload cycle.

  • Step 5: Agent presents a design section in chat, user validates
  • Step 6: Agent updates the HTML file to reflect the validated section
  • Step 7: Browser picks up the change within 3 seconds
  • Repeat: Steps 5-7 cycle for each design section

Phase 3 — Finalizepre-critique through post-critique

Before critique dispatch, the agent copies the live file to docs/mockups/ so the critique panel can access it at its configured path. After critique, if the design changed, the agent fully regenerates the HTML from the corrected design. Then it strips the refresh script, updates the design document header, and commits.

  • Step 8: Pre-critique: copy live file from /tmp to docs/mockups/{session-name}.html
  • Step 9: Critique panel runs (reads from docs/mockups/ — unchanged process)
  • Step 10: If critique modified the design: fully regenerate HTML at docs/mockups/{session-name}.html from the corrected design using the component reference (not surgical edit — full rewrite)
  • Step 11: Strip the LIVE-REFRESH-START / LIVE-REFRESH-END block from the docs/mockups/ copy
  • Step 12: Add **Mockups:** docs/mockups/{session-name}.html to the design document header (written AFTER copy)
  • Step 13: Commit design doc + mockup together

Success Criteria3 measures

Concrete, measurable criteria for validating that the live visualization system delivers on its promise. Each criterion maps to a specific observable behavior during a brainstorming session.

  • 1 Timing: The browser shows a meaningful visual artifact within 30 seconds of the agent beginning the design presentation phase — before the user provides feedback on the first section.
  • 2 Continuity: The artifact updates at least once per validated design section, with no manual browser refresh required.
  • 3 Parity: The final snapshotted artifact at docs/mockups/{session-name}.html is at least as informative as artifacts currently produced by the session-document-generator (tabbed layout, Mermaid diagrams, section breakdowns).

Testing Strategy5 categories

Verification areas for the live visualization system. Each category targets a specific layer of the architecture to ensure end-to-end correctness.

Refresh Script Stripping

  • Verify the <!-- LIVE-REFRESH-START --> / <!-- LIVE-REFRESH-END --> delimiters survive HTML generation and are cleanly removable
  • Test with edge cases: nested HTML comments within the block, minified HTML, multiline script tags
  • Verify the stripped file is valid HTML (no orphaned tags from the removal)

Mermaid Rendering

  • Verify Mermaid diagrams render correctly in the self-refreshing file over file:// protocol
  • Test lazy rendering on tab switch (existing pattern from session-document-generator)
  • Verify Mermaid syntax is valid before writing to file (reuse the verification step from session-document-generator)

Finalization Integrity

  • Verify the copy from /tmp/ to docs/mockups/ produces a valid standalone HTML file
  • Verify the **Mockups:** field in the design doc points to a file that exists
  • Verify the committed artifact renders correctly when opened after the session

Component Class Correctness

  • Each CSS class referenced in the component documentation must exist in the HTML template's <style> block
  • The reference doc and template are in the same file, but verify no class is documented that isn't defined (and vice versa)

Platform Behavior

  • Verify open / xdg-open fallback works on macOS and Linux (separate Bash calls, no chaining)
  • Verify graceful degradation when no browser is available (headless environment — warning, not error)

Known Limitations (v1)

  • Reload flash: Page goes white for a frame on each 3-second reload. Tolerable for a brainstorming artifact on a second monitor. If reported as a problem, a persistent web server with SSE becomes the justified upgrade.
  • Tailwind CDN over file://: All 8 existing mockup files already accept this risk. The 3-second reload makes CDN failures more visible but the root cause is unchanged.
  • No interaction capture: v1 is view-only. User feedback flows through conversation. If click/annotation capture is needed, HTTP POST to a lightweight server is the path.
  • Write atomicity assumption: The Write tool is atomic on macOS (write + rename), so the browser should not see truncated HTML mid-write.
  • macOS-primary: The open command is macOS-native. Linux fallback (xdg-open) is included but untested. Headless environments get a warning, not an error.
