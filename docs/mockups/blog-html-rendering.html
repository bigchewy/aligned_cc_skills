Workflow Changes flowchart

The existing 4-step workflow (Input, Generate, Review, Deliver) is preserved. Step 2 gains richer content generation with enhanced frontmatter and two MDX components. Step 4 gains context-aware output detection that routes to three possible delivery paths.

  • Step 1 (Input) and Step 3 (Review) are unchanged
  • Step 2 (Generate) produces enhanced frontmatter (heroImage, readingTime) and two MDX components (<Callout>, <CTA>)
  • Step 4 (Deliver) detects project context and routes to MDX, standalone HTML, or markdown output
  • Two new quality gates enforce hook/problem differentiation and meta description isolation

MDX Output Structure architecture

The MDX file is the primary deliverable. It stays as close to pure markdown as possible. Page layout (hero, title, byline, metadata) is driven by frontmatter and owned by the consuming site's page template. Only two MDX components are used.

  • Frontmatter carries title, date, description, category, featured, heroImage, and readingTime
  • Body starts with a hook paragraph, followed by PIEI sections (Problem, Insight, Evidence, Implication)
  • Pull quotes use standard > blockquote syntax, already styled by mdxComponents
  • description stays in frontmatter only (SEO/social cards) and is not rendered visually
  • author field omitted (single-author site, YAGNI)

Key Principles rules

  • No title/header/meta/byline markup in MDX body — all driven by frontmatter, rendered by the page template
  • Body starts with hook paragraph — matches the existing ewp-site blog post pattern
  • Only 2 MDX components — <Callout> and <CTA>, registered in the consuming project's mdx-components.tsx
  • Asset manifest — each post lists required images with paths following /images/blog/{slug}/ convention and recommended dimensions
  • Placeholder boxes — HTML preview shows placeholder boxes with alt text for images not yet placed

HTML Preview Pipeline flowchart

The HTML preview is a secondary artifact for review and sharing before publishing. It reads the project's CSS, extracts design tokens, and produces a standalone Tailwind CDN-powered HTML file that approximates the site's rendering.

  • Token extraction scans the @theme inline { } block from globals.css
  • Fallback chain: globals.css → brand/guidelines/visual-identity.md → aligned plugin standard palette
  • Renders full page layout: hero image area, title, category badge, reading time, date, article body, callout, CTA
  • Does NOT render site navigation, header, footer, or functional interactive elements
  • Output path: output/blog-{slug}-preview.html

Quality Gate Updates 3 changes

Two new quality gates are added to the existing 14, plus one modification. These address the observed problems of hook/problem repetition and meta description bleeding into visible content.

  • Gate 15 — Hook/Problem differentiation: the hook and the problem section's first paragraph must not share sentence openers, character introductions, or scene descriptions. Fails if >50% significant word overlap.
  • Gate 16 — Meta description isolation: the description frontmatter field must be a standalone summary, not an excerpt from the hook or problem section. Must not appear verbatim anywhere in the article body.
  • Gate 1 modification: updated structural elements to include Callout (the <Callout> component surfaces the post's key takeaway as a scannable element).
