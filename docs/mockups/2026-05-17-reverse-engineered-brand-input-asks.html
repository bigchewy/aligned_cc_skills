Reverse-Engineered Brand: Per-Tab Input Asks

What we still need from you, named per tab

Design for adding per-tab 'inputs needed' guidance to the reverse-engineered-brand framework's review.html artifact. Shipped back to prospects and clients alongside the build.

Goal

Make the review.html artifact name, in writing, what raw material would strengthen each tab. The reader is the prospect or client who already handed us their source material. The deliverable answers one question for them: "What else should I send you to make this report stronger?"

Today the framework knows when a tab has thin signal (it tags confidence: low, raises P0 OQs, drops the folder grade). It does not tell the client what category of artifact would have changed the result. The client reads "grade 2" without a path to grade 4.

Hard Constraints

  1. No PHASE 0 intake change. The build runs end-to-end on whatever the client already provided. Asks surface in the output, not the intake.
  2. Single source of truth per slice. Per-tab input asks live next to the slice's synthesis logic (each owning framework's frontmatter, or each non-framework slice's canonical reference). No parallel catalog.
  3. Context-bloat guard preserved. The orchestrator does not read slice draft bodies or source bodies. New computations operate over Source Registry metadata and pre-computed JSON only.
  4. Brand-voice review fires before the JSON is written. Client-facing copy passes the same voice gate as any other client deliverable.

Population Fit

Reader: A prospect or client who has engaged the brand team for positioning work. They handed over whatever source material they had. They know the brand intimately and they do not know our framework's internals. They will skim the artifact once, gather what they can, and send it back.

What the reader needs

  • A short, scannable list of what to gather (Critical first)
  • Confidence that we read what they sent. Acknowledgement before asking.
  • Specificity enough to delegate gathering to an assistant without a follow-up email

What the reader does not need

  • Framework jargon (slice, OQ, signal_tag, dispatch)
  • Build-time provenance (which sub-agent computed what)
  • Over-prescriptive shopping lists. Asking for "interviews where the buyer named the alternative AND raised the top 2 objections" buries the artifact under conditions a client will not screen for.

Goal-Metric Alignment

Goal: Convert review.html from a static delivery into a self-serve gather-list. The observable proxy: reduce follow-up "what did you mean by X?" emails after we ship a build to a client.

  • 1 Coverage: Every content tab in every build either shows zero Critical asks remaining, or shows at least one. No tab sits silently at grade 2 without a path to improvement.
  • 2 Specificity: Spot-check three real builds. Every Critical ask is quantified or typed, scannable in one line, and can be acted on without a follow-up email.
  • 3 Voice: Step 3.2c logs zero verification-gate failures on the first three real builds. The banned-phrase regex catches anything the sub-agent introduces.

These are observable from the build output. Track them on the next three real-client builds.

Out of Scope

  • Eric-facing internal QA. This design assumes the artifact is sent to clients, not used as internal scaffolding.
  • Auto-gathering from the client. The artifact names what is missing. Gathering the missing material remains a manual handoff.
  • Per-slice grading rubric changes. The existing grade rubric in prompt.md Step 3.2 is untouched.
  • The Open Questions schema itself. Input-type asks live on folders[], not on individual OQs. The OQ schema is unchanged.
  • The brainstorming skill's duplicated triage surfaces (live.html widgets vs. critique HTML). Tracked separately as a kanban entry, not folded into this design.

Source of Truth

Each owning framework declares its inputs in its own frontmatter via a new structured field, input_asks:

input_asks:
  - tier: critical          # critical | recommended | optional
    ask: "3-5 customer interview transcripts including the customer's role"
  - tier: recommended
    ask: "Sales call recordings or transcripts"
  - tier: optional
    ask: "Support tickets surfacing recurring pain language"

tier drives which section of the consolidated list the ask appears in. ask is the medium-prescriptive client-facing copy. The schema is intentionally minimal. No satisfied_by_tag. No per-ask fulfilled boolean. The "what was provided" surface lives at the folder level, not per-ask.

The two non-framework slices keep the same shape:

  • frameworks/reverse-engineered-brand/audience-taxonomy.md gets a new ## Ideal inputs section with input_asks blocks for the segments/channels surface.
  • The Competitive Context tab's input asks live inline in frameworks/reverse-engineered-brand/prompt.md PHASE 1.5a where the orchestrator already aggregates that data. One small string array in the framework prompt. No new file.

Multi-slice Folder Merge Rule

Several folders host more than one slice. strategy/ has positioning and narrative. language/ has messaging and voice. market/ has competitive and alternatives. proof/ has proof-points, optional clinical-evidence, and optional compliance.

PHASE 3.2 aggregates input_asks across all slices that contributed to each folder, then dedupes by ask text (case-insensitive trim match). When two slices produce identical asks, the higher tier wins (critical beats recommended beats optional). Final order within each tier: deterministic by first-seen.

Renderer

review-template.html changes:

  1. Add a third Overview sub-tab. The Overview tab already has two sub-tabs (Executive Summary, Sections at a Glance) wired through switchSubTab('overview', ...). Add Inputs Needed as the third. Same CSS, same JS hook.
  2. Render the consolidated list inside the new sub-tab, grouped by tier (Critical, Recommended, Optional). Each item shows the ask plus the tab name as an inline tag. Item rows are anchor links into the per-tab callouts.
  3. Render per-tab callouts under the existing per-folder summary banner on each single-instance content tab (Strategy, Language, Market, Proof, Design when present). Callout content: this tab's provided_summary paired with this tab's input_asks.
  4. Multi-instance folders skip the per-tab callout. Personas, audiences/segments, audiences/channels can have many sub-files; collapsing per-role evidence into one merged callout loses signal. v1 ships the consolidated Overview list for these. Per-instance callouts are deferred (see Open Questions).

render-review-html.md extends to consume folders[].input_asks and folders[].provided_summary. No new sub-agent.

Brand-Voice and provided_summary Sub-Step

PHASE 3 gains two steps between 3.2 (build folders) and 3.6 (write JSON):

Step 3.2b: Brand-voice rewrite + provided_summary generation Dispatch one sub-agent (subagent_type: general-purpose) with these inputs: (a) the array of all ask strings across all folders; (b) per-folder lists of (source-id, source-type, signal_tags) tuples from the Source Registry (registry metadata only, no source bodies); (c) the path to the brand voice file. Resolution order: brand/guidelines/brand-voice.md relative to the {brand-folder-path} first; ~/.claude/brand-voice.md second; pass-through if neither exists. Pass-through means: keep the source strings unchanged. The voice file path resolves at runtime, not at framework authorship time, which fixes the portability issue. The sub-agent returns: the voice-revised ask strings, and one provided_summary string per folder, generated from the registry tuples and capped at 25 words. The orchestrator merges both back into the folders[] structure.
Step 3.2c: Verification gate Three checks, all hard-fail.
  1. Array length. Count of asks in = count of asks out. The sub-agent cannot drop or add entries.
  2. Banned-phrase regex on every post-pass ask and provided_summary string. Patterns: em dashes, "It's not X, it's Y" construction, AI buzzwords (leverage, seamless, unlock, streamline, delve, robust, cutting-edge, transformative, elevate, revolutionize, crucial, essential). On a match, fail with the offending string and the pattern.
  3. Tier preservation. Each ask's tier value in the output array equals its tier in the input array, by index.

On any failure: abort the build with a named failure list. Voice failures should be rare; when they happen, the message is "the voice file produced a phrase that violates the banned list — review the file or the sub-agent prompt." No silent fallback.

5 Inputs Needed as a third Overview sub-tab, not a 10th top-level tab; not a banner at the top of Overview
▾
Alternatives considered: new top-level tab; always-visible banner under the Overview header.

Sub-tab pattern is already wired. A banner-always-visible alternative was considered for "acknowledgement before asking" but loses scannability when the list is long. The Inputs Needed sub-tab plus per-tab callouts hits the same beat without the noise.

6 Brand-voice + provided_summary fire in one PHASE 3.2b sub-agent, followed by a Step 3.2c verification gate
▾

JSON is the canonical text. Editing HTML mixes copy review with template debugging. The verification gate catches voice drift and array-shape errors deterministically.

7 Tier comes from frontmatter author at framework-authorship time, not derived from OQ P0/P1/P2
▾
Alternatives considered: map P0 to Critical, P1 to Recommended, P2 to Optional.

Per-OQ impact and per-tab input criticality are different atoms. Static tier is stable, explicit, auditable.

▾

Single-tag emission was too noisy a signal to drive a checkmark ("3-5 transcripts" satisfied by one tag is a lie). Folder-level provided_summary carries the "what you sent" signal in prose, which is harder to game. Revisit in v2 with a count-based gate if needed.

▾

Folders/strategy hosts positioning and narrative; both will name interview-style inputs. Dedupe-by-text keeps the consolidated list clean. Higher tier wins matches reader intuition.
