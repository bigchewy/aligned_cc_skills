Eval Auto-Run Integration

Wiring the Promptfoo eval framework into the finishing-a-development-branch workflow

Auto-run scoped evals when LLM behavior surface files change on a branch. No changes to the eval framework itself. Scope runs to affected scenarios only. Handle missing API keys and config gracefully.

System Overview

The eval auto-run system consists of two config files that gate and scope eval execution, an 8-step inline logic flow in the finishing skill, updates to seven cross-referenced files, maintenance hooks to keep the trigger map current, and validation tests for the YAML configs.

Config FilesYAML

Two separate YAML files serve different consumers with different requirements. The surface config is the broad gate (~476 files matching glob patterns); the trigger map is the narrow scope (only files with existing scenarios). Merging them would blind Step 1b to ~99% of the surface and break eval-audit's gap detection.

  • eval-surface.yaml defines the full LLM behavior surface via glob patterns. Used as the gate check ("did anything relevant change?") and by eval-audit for coverage gap detection.
  • trigger-map.yaml maps specific changed files to specific eval scenarios. Paths in paths arrays are repo-root-relative; paths in scenarios arrays are e2e/-relative. Used for scoping after the gate passes.
  • Invariant: every path in trigger-map must match at least one eval-surface pattern. eval-audit cross-validates this.
  • YAML structure constraint: both files must remain flat structures (simple arrays of strings or simple arrays of objects with string arrays). No YAML anchors, aliases, or nested structures. Keeps Claude-as-parser reliable.

Step 1b Inline LogicCore Flow

The eight-step process that replaces the placeholder in the finishing-a-development-branch skill. Each step has a clear gate/action/outcome pattern. The flow is non-blocking by default, only hard-stopping on actual eval failures.

End-to-End Flow

Eight steps from API key check through completion summary. Four early exits (API key missing, config missing, no surface changes, no trigger entries) keep the common case fast. Evals run sequentially to avoid API rate limit collisions.

Gates and GuardsNon-blocking

The design follows the codebase's three-tier pattern: hard blockers for known breakage, non-blocking reporters for gaps, and silent skips when no precondition is met. Most gates are non-blocking.

  • API key guard (Step 1): Checks ANTHROPIC_API_KEY via printenv. OPENAI_API_KEY is not checked because the distinctness scorer is a standalone post-hoc tool, not wired into promptfoo assertions. Non-blocking skip with message.
  • Config guard (Step 2): Reads e2e/eval-surface.yaml and e2e/trigger-map.yaml. If either is missing or empty, reports the specific missing file and skips. Non-blocking.
  • Surface gate (Step 3): Matches git diff --name-only against eval-surface.yaml patterns using prefix matching for globs and exact match for specific-file patterns. Silent skip if nothing matches.
  • Coverage summary (Step 5): Counts mapped vs. unmapped surface files. Summary count avoids noise at ~99% unmapped. Suggests running /aligned:eval-audit.
  • Hard stop (Step 7): Only triggered on exit code 1 from promptfoo. Shows scorecard and dispatches eval-failure-triage skill.

Decision Log5 decisions

Key design decisions that shaped this integration. Each decision has a clear rationale grounded in the existing codebase patterns and data model.

  • D1 - Strict file mapping: Scenario YAML files use explicit file:// references. The data model is per-file, not per-category. Category-based scoping produces noise (e.g., Dunford rubrics on Walling changes measure nothing). eval-audit handles "no scenario exists" gaps.
  • D2 - Separate config files: Different consumers, different requirements. Surface config is the superset (~476 files); trigger-map is the subset. Merging would make Step 1b blind to ~99% of the surface and break eval-audit's gap detection. Invariant: every trigger-map path must match at least one surface pattern.
  • D3 - Skip with summary warning: Follows the codebase's three-tier pattern: hard blockers (known breakage), non-blocking reporters (gaps), silent skips (no precondition). Missing coverage is tier 2. Summary count avoids noise at ~99% unmapped.
  • D4 - No script, inline logic: Claude Code is the runtime with native Read/Bash/Grep. No root package.json, no yq installed. Existing skill pattern (test/build/deploy detection) uses prose instructions. CI script is a separate future deliverable.
  • D5 - Strict mapping is forward-looking: At current scale (3 scenarios), "run all" would be simpler with negligible cost. Strict mapping pays off at ~15-20 scenarios. Investing now avoids a refactor when scenario count grows.

Skill Maintenance HooksKeep current

When new eval scenarios are added, the trigger-map must be updated. Three existing skills get concrete instructions added to their workflows to keep the mapping in sync.

  • add-advisor (Step 7): After creating the eval scenario, add a trigger entry mapping the new advisor prompt path to the new scenario path.
  • add-framework (Step 6): Same pattern. Map the new framework prompt path (and examples/anti-examples) to the new scenario path.
  • eval-audit (Phase 3): When filing coverage gaps as Kanban entries, include trigger-map update in the remediation checklist (add "AND add corresponding entry to e2e/trigger-map.yaml" to the Expected field).

What This Design Does NOT Change

Explicit boundaries to prevent scope creep during implementation.

  • Eval framework itself: Promptfoo config, scenarios, scorers, fixtures remain untouched.
  • eval-audit core logic: Reads from explicit config instead of fallback heuristics.
  • Hook system: No new entries in hooks/hooks.json.

Validation Tests3 suites

Validation tests for the YAML config files, using the existing e2e/tests/ pytest infrastructure. These ensure config files stay in sync with the filesystem and with each other.

  • No orphan patterns: every glob in eval-surface.yaml matches at least one file on disk.
  • No broken paths: every path in trigger-map.yaml exists on disk, and every scenario path resolves relative to e2e/.
  • Cross-validation invariant: every trigger-map path matches at least one eval-surface.yaml pattern.
  • No orphan trigger entries: every scenario in trigger-map.yaml also appears in e2e/promptfooconfig.yaml's scenario imports.
