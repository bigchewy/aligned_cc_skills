Strategy Mode and Shared Runners

Refactoring Brainstorming's Business and Authoring modes into a single dispatch layer

Topic: framework-runner-refactor · 2026-05-09 · Software brainstorm · docs/plans/2026-05-09-framework-runner-refactor-design.md

Goal

Replace brainstorming's Business and Authoring modes — both running hardcoded phase scripts that duplicate registered frameworks — with a single strategy mode that dispatches to one of three engines: a registered framework, an advisor-led conversation, or open exploration. Brainstorm scaffolding (project scan, intake, critique, viz, commit, handoff) wraps the selected engine.

Three real use cases user-confirmed

1. Apply a known framework

You already know which framework fits — April Dunford 5-Components, 80/20 Audit, Accusation Audit. Generic 4-phase RCA is in the way.

2. Think with a specific advisor

You want Wise Eric, Diana Chapman, April Dunford as a thinking partner. Process-light, persona-led conversation.

3. Strategic exploration

Strategic question without a chosen framework. The Goal → Problems → Root Causes → Solutions shape is wrong because nothing is being diagnosed.

Not a real use case: tactical sequencing. The current Business mode operational-vs-diagnostic depth branch (business.md:43-71) solves a problem the user does not have. Removing it.

What changes for the user

Today

- 5 modes, including separate Business and Authoring with hardcoded phase scripts

- Generic facilitator voice, no advisor persona

- Framework registry (147 entries) cannot be invoked from inside a brainstorm

- Operational-vs-diagnostic depth branch chooses for you, often wrong

After refactor

+ 4 modes: Software, Strategy, Research, Planning

+ Strategy auto-detects best framework or advisor, offers with override

+ Brainstorm scaffolding (scan, critique, viz, commit, handoff) wraps any of 147 frameworks or 70 advisors

+ No depth branch — engine choice replaces it

D1 — Collapse Business + Authoring into one strategy mode

The recently-extracted shared scaffolding (commits 89b4cad, eb4c869) shrunk mode files toward "config + the mode-specific bit." The mode-specific bit in Business and Authoring is no longer a distinct process — both are "facilitate dialogue → produce design doc → critique panel" with different critic pools and templates. That is a config table, not a mode file.

Decision Replace business.md and authoring.md with one strategy.md. Brainstorming becomes a 4-mode skill.
Why Software/Research/Planning stay separate: they have unique processes (Architect auto-consult mid-flow; Skeptic Pass + corpus survey; portfolio sequencing). Business and Authoring don't.

D2 — Detection extends contextual-recommendation

skills/_shared/contextual-recommendation.md already abstracts advisor vs framework field-mapping. Add a multi-entity mode (framework-or-advisor) that scores both registries in one pass. Auto-select vs shortlist confidence machinery already exists.

Decision Engine detection lives in strategy.md Phase 1 by invoking the extended contextual-recommendation. Not in SKILL.md Step 1.
Constraint Mode detection (which mode) and engine detection (which framework/advisor) are different questions. Layering them muddies both.

Decision Both top-level use-framework/use-advisor and strategy.md invoke the same shared runner. Bidirectional contract: an advisor in mid-conversation can invoke the framework runner; runner returns control to the advisor on completion.

D4 — Metadata location

New fields needed: deliverable_type, default_critic_advisors, follow_on_frameworks.

Registry only

+ One file edit; trivial blast radius

- Authoring-time invisibility for framework writers; closing-phase output drifts from runner expectation

Both (registry authoritative)

+ Self-checking loop catches drift

+ Framework authors see deliverable_type at the top of their prompt

- Migration script touches 147 prompt.md files (mechanical)

Decision default_critic_advisors + follow_on_frameworks: registry only. deliverable_type: registry authoritative + mirrored to prompt.md frontmatter via one-shot migration. CI eval flags drift.

Sequencing — strict ordering required

Architect flagged the critical path: Step 4 (mode collapse) cannot ship before Step 2 (metadata migration) completes, or Phase 3 dispatch crashes on missing deliverable_type. Steps 0–3 are non-breaking; Step 4 is the user-visible cutover.

Step 0: Preconditions
Step 1: Extract runners
Step 2: Metadata migration
Step 3: Multi-entity scoring
Step 4: Cutover
  1. Step 0 (preconditions, parallel): Resolve KB-033 (empty purpose fields). Audit and clean name field hygiene in frameworks/registry.yaml.
  2. Step 1 (extract runners, non-breaking): Move use-framework Steps 4-5 to _shared/framework-runner.md. Same for use-advisor. Backward-compat eval verifies identical behavior.
  3. Step 2 (metadata, non-breaking): Define deliverable_type taxonomy. Manually classify all 147 frameworks. Add registry fields. Run migration script. Add CI drift check.
  4. Step 3 (multi-entity scoring, non-breaking): Extend contextual-recommendation. Calibrate thresholds via new eval scenarios.
  5. Step 4 (cutover, user-visible): Ship strategy.md + checklist + template. Update SKILL.md to 4 modes. Delete business.md, authoring.md, their checklists and templates. Bump plugin version.

Cross-cutting risks

Critical-path coupling

Steps 2 + 4 share dispatch table. deliverable_type must be populated before strategy.md ships, or fallback runs everywhere.

Confidence calibration

Auto-select vs shortlist thresholds for merged scoring need eval-driven calibration. Too lenient → bad fits; too strict → fallback never fires.

Bidirectional runner contract

Advisor in mid-conversation must be able to invoke framework-runner; runner must return control to the advisor. Existing Composability rule extends.

Strategy vs Research disambiguation

New rule needed: evidence map from external corpus → Research; decision/plan informed by existing context → Strategy.

Taxonomy edge cases

Frameworks producing both content + decision (e.g. 5-components-positioning). Validate primary-tag rule against 10-15 ambiguous frameworks before classifying all 147.

Testing strategy

Per CLAUDE.md TDD rule: every async operation that can fail in production has both success AND error tests. Eval scenarios calibrate confidence thresholds; unit tests cover the migration script.

Eval scenarios

  • strategy-mode-engine-selection.yaml — calibrate auto-select / shortlist / fallback ladder. Strong framework match, strong advisor match, weak match, no signal, shortlist case.
  • framework-runner-extraction.yaml — use-framework and strategy-mode invocations produce identical execution. WAIT discipline, voice carrying, intake-gate behavior.
  • deliverable-type-dispatch.yaml — Phase 3 picks correct template + critic pool per type. Includes missing-deliverable_type fallback path.
  • use-framework-backward-compat.yaml — direct /aligned:use-framework invocation produces identical pre-refactor behavior.

Unit tests

  • tools/test_sync_framework_frontmatter.py — idempotency, YAML escaping for quoted names (5-components-positioning has embedded quotes), missing prompt.md, missing registry entry.

Error paths (mandatory per TDD rule)

  • Framework runner with missing prompt.md → existing error preserved
  • Framework runner with empty prompt.md → existing error preserved
  • Framework runner with broken advisor reference → generic facilitator voice + Decision Log entry
  • Strategy mode with missing deliverable_type → fallback critique pool + warning to user
  • Strategy mode with project scan failure → engine selection on topic alone + user notification
  • Contextual-recommendation multi-entity mode with empty registries → graceful prompt for input
