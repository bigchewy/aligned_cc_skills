Brainstorming Mode Naming and Routing

Eliminate silent mis-routes; collapse Business+Authoring into Authoring; rename Planning→Roadmap

Composes with docs/plans/2026-05-09-framework-runner-refactor-design.md. Post-critique revision: 5 HIGH + 7 MEDIUM + fact-check corrections applied. Design doc: docs/plans/2026-05-17-brainstorming-mode-naming-and-routing-design.md

Goal

Eliminate the silent auto-routing failure that sent a deck-building workflow to Planning mode (wrong) when Authoring mode (right) was sitting one mode away. The user could not see, much less correct, the routing choice — the brainstorm just began in the wrong mode and produced a too-high-level deliverable.

  • Collapse the Business+Authoring overlap that hid Authoring's existence (extending the May 9 plan) — name the result authoring rather than strategy for discoverability.
  • Rename Planning → Roadmap so it stops colliding with all the other "planning" activity in the skill ecosystem.
  • Always-ask routing discipline so the router never silently commits to a mode without user confirmation.
  • Keyword expansion for both Authoring (deck/pitch/memo/presentation) and Roadmap (big-idea/break-down/decompose).
  • Authoring's no-framework fallback uses Software-mode-style structured Q&A — not "advisor-led free exploration."

Final Mode Shape — 4 Modes

The four modes after this design ships. Software unchanged; Business + Authoring collapse into Authoring; Research unchanged; Planning renamed to Roadmap.

software

Unchanged. Designs runtime/code changes via Architect-led structured Q&A → design doc → writing-plans.

authoring

Replaces business + authoring. Authors any document — memos, decision docs, decks, positioning briefs — via framework-runner dispatch with deliverable-type-driven post-engine routing.

research

Unchanged. Synthesizes external evidence into a ranked recommendation memo.

roadmap

Renamed from planning. Sequences multi-feature portfolios into a roadmap + spawn-list portfolio for future brainstorms.

Pattern unification The Software-mode Q&A pattern becomes a generalized "structured Q&A with auto-consulted topic advisor." Software mode is the specific case where the topic advisor is The Architect; Authoring's no-framework path uses the highest-scoring domain advisor (or Wise Eric as default).

Always-Ask Discipline

The router never silently commits to a mode. Session-scoped: ask on first invocation; skip on subsequent same-mode invocations within the conversation. Four sub-tabs below detail (a) the always-ask spec with error handling, (b) the picker label format rendered as it appears to the user, (c) the session-marker fallback rule, and (d) before/after flowcharts.

The Step 1 contract: always present the 4-mode question on first invocation; skip only on subsequent same-mode invocations within the conversation, or when an explicit --mode arg is passed.

  • First invocation: Step 1 always presents the 4-mode question with the auto-detected mode pre-selected as default. One-tap to confirm, one-tap to pick another.
  • Subsequent same-mode: skip the confirmation if the auto-detected mode matches the previous brainstorm's mode in this conversation.
  • Subsequent different-mode: re-ask. Signal drift means the user moved to a new task surface.
  • Mode explanation block: moves into the question prompt itself (inline option descriptions) so users see what each mode does as they pick. "Why:" line dropped (M8 — happy talk). Build & ship / Diagnose / Sequence grouping dropped (M8 — 4-mode flat list).

One Skip Condition

One condition bypasses the confirmation even on first invocation, representing pre-disambiguated input.

1. Explicit mode arg

/aligned:brainstorming --mode software "topic" — the user has already chosen.

Future work: structural spawn-brief marker A literal [spawn-brief target=X] prefix that the spawn-brief template generates would enable safe pre-disambiguation. The verb-prefix heuristic (e.g. "design...", "compose a roadmap for...") was rejected: it would fire on free-form user prompts like "design the auth refactor", re-introducing the silent mis-route this redesign eliminates. spawn-brief-template.md L25–27 explicitly states the router uses topic-keyword signal detection on the paragraph prose, and target_mode is not consumed by any parsing layer.

Error Handling

Four edge cases for the always-ask question.

  • No answer (timeout): default to the pre-selected mode after a 60-second wait (standard AskUserQuestion default-on-timeout behavior).
  • Non-mode answer or "Other": surface a one-line follow-up — "Describe in one sentence what you're trying to produce — a document, code change, evidence synthesis, or multi-piece breakdown." Apply signal detection to the free-text answer; if still ambiguous, route to Authoring (which absorbs Business's diagnostic functions post-collapse, including the prior "I'm not sure" handling).
  • Mid-brainstorm re-ask: if the user explicitly says "wrong mode" or "switch modes," re-fire the always-ask question with no pre-selection.
  • Post-collapse fallback for "I'm not sure": the current SKILL.md L105 "I'm not sure" → Business route MUST be updated to "I'm not sure" → Authoring as part of the rename (Business doesn't exist post-collapse).

The session-marker optimization is best-effort, not load-bearing. It degrades gracefully to always-ask under uncertainty rather than to silent false-skip.

Rule If the model cannot confidently recall the prior brainstorm's mode from conversation context — e.g., after context compaction, sub-agent invocations, parallel/forked conversations, or any uncertainty — fall through to always-ask.

Why this matters

The session-marker detection is purely model-side: the model checks its own conversation context — "have I already routed a brainstorm in this conversation?" There are no /tmp files, no env vars, no external state. Under model uncertainty, the safe default is to always-ask, NOT to guess and silently skip the confirmation. Silent-skip on uncertainty would re-introduce the failure mode this redesign eliminates.

  invoke([User invokes /aligned:brainstorming

4-mode question])
  sameAuto -- yes --> skipAsk[Skip confirmation,
route to same mode]
  sameAuto -- no --> ask
  skipAsk --> begin([Brainstorm begins])
  ask --> begin
  • Compaction: after context window pruning, prior-mode recall is no longer guaranteed — always-ask.
  • Sub-agent invocations: if a sub-agent fired the prior brainstorm, the main model may not have that turn in scope — always-ask.
  • Parallel/forked: branched conversations may diverge from a shared parent's prior brainstorm — always-ask.
  • Any uncertainty: default is always-ask. Friction (one extra confirmation) is cheaper than mis-route (silent wrong mode).
