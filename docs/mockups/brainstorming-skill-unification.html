Brainstorming Skill Unification

Merging /aligned:brainstorming and /aligned:business-brainstorming into a single entry point

Eliminates user-facing choice between two brainstorming skills by introducing a thin router that auto-detects mode (software vs. business) and hands off to mode-specific process files. Post-critique design: scan dispatch moved after mode detection, signal precedence added, mode switch escape hatch, error handling for missing mode files. Version bump: 0.12.0 to 0.13.0.

File Layoutarchitecture

The unified skill collapses two top-level directories into one. A modes/ subdirectory holds process files Read by the router at runtime (inline context, not sub-agent dispatch). This differs from the workers/ convention.

  • SKILL.md becomes a thin router (~60-80 lines) instead of the full software process
  • modes/software.md and modes/business.md hold mode-specific processes
  • business-critique-checklist.md moves into the brainstorming directory (renamed)
  • business-brainstorming/ directory is deleted entirely

Router Patternarchitecture

The router follows a detect-scan-handoff pattern. It classifies mode first, then dispatches a mode-aware scan, then hands off to the mode file with explicit paths. The router passes {base-directory} and the orchestration path so mode files never derive paths themselves.

  • Step 1: Detect mode from topic signals (primary) and environment (tiebreaker) (D8)
  • Step 2: Dispatch scan with mode context so scanner knows what to emphasize (D7)
  • Step 3: Hand off with explicit checklist path, {base-directory}, and orchestration path (D5)
  • Error guard: if mode file cannot be Read, STOP and report incomplete installation

Step 1: Detect Moderouter

Mode classification uses two signal channels with explicit precedence: topic keywords override environment signals (D8). A user in a code repo asking about "pricing strategy" routes to business mode. When signals are clear, the router auto-routes with a one-line escape hatch. When ambiguous, it asks exactly one question (D3).

  • Signal precedence: topic keywords > environment context (environment is a tiebreaker only)
  • Software signals: features, APIs, bugs, refactoring, architecture, code, testing, data models
  • Business signals: strategy, sales, marketing, positioning, pricing, proposals, planning
  • Environment (tiebreaker): code files (package.json, Cargo.toml, etc.) vs. docs-only / Obsidian vault
  • Escape hatch: "If this isn't right, just say so and I'll switch." -- always appended to auto-route messages
  • Fallback: one question -- "Is this software/technical or business/strategy?"

Step 2: Project Scanrouter

The router dispatches a project scan agent in the background after mode detection, not before (D7). This lets the scanner know the mode so it can emphasize code artifacts (software) or domain materials (business). Both modes consume scan results, so centralizing dispatch here eliminates duplication and the fragile "don't re-dispatch" instruction pattern (D6).

  • Mode-aware dispatch: scanner receives the detected mode to tailor its emphasis
  • Background dispatch via Task tool (subagent_type=general-purpose)
  • Non-blocking -- router proceeds to hand-off without waiting for scan results
  • Mode files reference scan results as "already dispatched by the router"
  • Scan gate still enforced in software mode: no technical questions until scan completes

Step 3: Hand Off to Moderouter

The router reads the appropriate mode file and passes explicit paths: the checklist, {base-directory}, and the shared orchestration file path. Each mode file then runs its full process independently. If the mode file cannot be Read, the router STOPs with an installation-incomplete message instead of failing silently.

  • Software hand-off: reads modes/software.md, passes design-critique-checklist.md, {base-directory}, orchestration path
  • Business hand-off: reads modes/business.md, passes business-critique-checklist.md, {base-directory}, orchestration path
  • Explicit paths prevent fragile name derivation from mode name (D5)
  • Error handling: if Read fails on the mode file, STOP and tell user the plugin may be incomplete
  • Mode files own the entire process from first question to final commit

Design Critique in Mode FilesD9

Design Critique (critiquing existing designs brought to the skill) stays in each mode file as a secondary capability, not a third router path. Each mode uses its own checklist for critique, so the critique behavior naturally differs per mode. This avoids elevating a 2-3 line section into a full routing decision (D9).

  • Software critique: uses design-critique-checklist.md with division-of-labor fact-checking
  • Business critique: uses business-critique-checklist.md with all-critics fact-checking + WebSearch
  • Not a third router path: Design Critique is a secondary use case within each mode, not a distinct brainstorming process
  • Rejected alternative: shared critique file across modes (checklists differ, so one file would need conditionals)

Decision Log9 decisions

Key architectural decisions with rationale and rejected alternatives. Each decision is referenced by ID (D1-D9) throughout the other tabs. D7-D9 were added after the design critique round.

# Decision Rationale Rejected
D1 Thin router + mode files Processes are fundamentally different (flat Q&A vs 4-phase gated); merged file would be 400+ lines of conditionals Full merge, keep separate + alias
D2 modes/ subdirectory New convention for files Read inline by a router. Distinct from workers/ (sub-agent dispatch) and references/ (static reference material) Inline in SKILL.md, references/, reuse workers/
D3 Auto-detect with fallback Environment signals alone are insufficient for non-code contexts; one clarifying question is acceptable Fully automatic, always ask
D4 Preserve business 4-phase gates Gates prevent jumping to solutions; confirmed valuable by user Flatten to fluid Q&A
D5 Explicit checklist path Checklists have different filenames after colocation; name derivation was fragile Derive from mode name, same filename in subdirs
D6 Remove scan dispatch from modes Cleaner than "do not dispatch again" prose; mode files reference results, not dispatch logic Keep dispatch + "don't re-dispatch" instruction
D7 Dispatch scan after mode detection Scanner should know the mode to emphasize code artifacts (software) or domain materials (business). Dispatching before wastes the opportunity for mode context. Dispatch before detection
D8 Topic signals over environment A user in a code repo asking about "pricing strategy" is doing business work. Environment is a tiebreaker, not a primary signal. Environment-first
D9 Design Critique stays in mode files Design Critique is a secondary capability (2-3 lines), not a distinct process. Each mode uses its own checklist, so no shared path works. Third router path, shared critique file
