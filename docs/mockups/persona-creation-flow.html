Persona Creation Flow

Guided cold-start path for the persona-panel skill

Adds automatic persona creation when docs/personas/ is empty, replacing the current dead-end with a four-phase guided flow. Scans existing docs (with false-positive handling), asks adaptive questions, confirms the persona set, generates complete 20-field files, prompts for content, and hands off to Stage 2.

End-to-End Flow

The flow triggers when persona-panel finds no persona files. An opt-out prompt gives the user an escape hatch to manual creation before entering the four phases. After file generation, a content prompt bridges to the first panel run.

Phase 1: Context Detectionpassive

Scans for existing buyer/persona documentation before asking questions. False-positive handling caps presented files at 5 and frames them as opt-in. If the user declines found docs, the flow falls back to full Q&A.

Sources scanned in order of specificity. Earlier sources take priority.

  • docs/ directory — files with buyer, persona, ICP, audience, or customer keywords in filename or content
  • content/ and marketing/ — marketing briefs, sales collateral, positioning docs
  • CLAUDE.md / project instructions — target audience, product description, market context
  • README.md — product description, value prop, who it's for

Keyword matches on filenames alone are low-confidence. The design addresses this with caps and opt-in framing to prevent false positives from derailing the flow.

  • 5-doc cap — show at most 5 files regardless of how many match; prevents overwhelming the user
  • Opt-in framing — "I found these docs that might describe your buyers: [list]. Should I use any of these as a starting point, or skip straight to questions?"
  • Filename-only matches are low-confidence — e.g., api-customers.md may be an API doc, not buyer research
  • Decline fallback — user says no to all docs, flow proceeds to full Q&A as if nothing was found

Phase 2: Q&Ainteractive

Adapts depth based on how much context Phase 1 found. Rich context yields confirmation plus 1-2 gap-filling questions. Minimal context triggers the full five-question sequence. Concrete heuristics determine when to probe deeper and when to move on. Hard cap at 7 total questions.

When Phase 1 found relevant documentation and the user accepted it, the Q&A confirms extracted buyer types and fills gaps with targeted questions.

  • Extract buyer types from scanned docs and present for confirmation
  • 1-2 targeted questions to fill gaps: psychology, objections, communication style
  • Group naming inferred from buyer set (e.g., b2b-buyers/, enterprise/)

When no relevant docs were found (or user declined them), the full question sequence runs. Questions are asked sequentially, one at a time. Q2 accommodates single-buyer products.

  • Q1: "What does your product/service do?" (skip if obvious from CLAUDE.md/README)
  • Q2: "Who are the distinct buyer types you sell to? Could be one, could be several — just roles or titles."
  • Q3: "What's the main problem each buyer is trying to solve?"
  • Q4: "What makes each buyer type skeptical?"
  • Q5: "How do these buyers talk?" (formal/casual, data/story, technical/non-technical)

Single-buyer case: If the user names only one buyer type, proceed normally. A single-persona panel has reduced diagnostic value (no cross-persona contrast) but is still useful.

The Q&A adapts dynamically to answer quality using concrete heuristics. Hard cap at 7 questions total regardless of path.

  • Rich answer (2+ sentences per buyer) — covers motivations or objections without prompting; skip follow-up on that topic
  • Thin answer (single phrase, role title only) — no detail on motivations; ask a follow-up to deepen (e.g., "What keeps [role] up at night about this problem?")
  • 7-question hard cap — after 7 questions, proceed to Summary with what you have regardless
  • Group naming — inferred from buyer set; if unclear, becomes one of the questions

Phase 3: Summary Approvaldecision

All proposed personas are displayed in a table for user approval before any files are written. The user can adjust names, add or remove personas, or change archetypes. This is the single gate between planning and generation. Aborting here writes no files.

  • Table format — file name, display name, archetype, and key differentiator for each persona
  • Batch approval — approve the entire set, not individual personas (Decision #4)
  • Adjustment loop — user can request changes and see the updated table before proceeding
  • No partial generation — if user aborts, no files are written; next invocation restarts from Phase 1

Phase 4: File Generationgeneration

On approval, all persona files are generated in a single batch using the template at references/persona-template.md. Every field is populated with no TODOs or placeholders. After generation, a content prompt bridges to the first panel run.

  • Template source — references/persona-template.md defines all 20 fields
  • Data sources — Q&A answers + extracted doc context fill the fields
  • Inference — fields not explicitly addressed get reasonable defaults (e.g., "Years in role" estimated from archetype)
  • Batch write — all files written at once after approval, no incremental saves

Abort behavior is fully specified: restart-not-resume, clean exit confirmation, no partial file writes.

  • Trigger words — "stop", "nevermind", "I'll do this later", or other exit signals
  • Clean exit — no files written, confirmation message: "No files written. Next time you invoke the persona panel, it'll offer this flow again."
  • Restart, not resume — re-invocation always starts from Phase 1; Q&A is short enough that restart cost is low
  • Two natural exit points — opt-out prompt at flow start and approval gate in Phase 3; no mid-Q&A abort prompts (avoids friction in the common case)
  • No partial files — files are only written after Phase 3 approval; abort at any prior point has zero side effects

Edge cases explicitly handled in the design.

  • User aborts mid-flow — stop cleanly, no partial files written. Next invocation restarts from Phase 1 (no resume).
  • Very thin Q&A answers — generate complete personas anyway using reasonable inference. The calibration system flags generic personas over time (5+ runs of monotone verdicts).
  • Personas exist elsewhere — creation flow only triggers when docs/personas/ has no persona files at all. Existing groups are handled by Stage 1's normal group selection logic.
  • Template file missing — error clearly, do not generate malformed files.

Explicit boundaries define what the creation flow does NOT do. These prevent scope creep and keep the flow focused.

  • No editing — does not edit or update existing personas
  • No multi-group — does not create personas for a second group in the same invocation
  • No validation — does not validate personas against real content (that is the panel's job)
  • 7 question cap — does not run more than 7 Q&A questions

Success Criteria3 criteria

Three measurable criteria define whether the creation flow is working as designed. These are verifiable in practice, not aspirational.

  • Cold-start elimination: A user invoking /aligned:persona-panel in a repo with no personas reaches their first panel evaluation without leaving the skill or manually creating files.
  • Structural validity: Every generated persona file passes template validation — all 20 bullet fields populated, no TODOs, no placeholders. Review Lens fields are specific enough to differentiate persona reactions (not generic "wants value" statements).
  • Time to first panel: The creation flow completes in under 10 conversational turns (context detection + Q&A + approval), getting users to their first evaluation quickly.
