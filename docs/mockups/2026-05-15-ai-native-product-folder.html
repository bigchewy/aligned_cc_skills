The AI-Native Product Folder

Sibling to brand/ and sales/. Holds the operational and product facts a digital-health marketing-asset generator must cite without hallucinating — PMPM, EHR footprint, coverage matrices, value-based-contract structures, clinical workflow, regulatory tailwinds. v0.2 integrates findings from a four-critic panel (Yoo / Dunford / Dixon / Architect).

Date 2026-05-15 Topic ai-native-product-folder Mode Authoring (strategy) Revision v0.2 Target: digital health companies

Critique panel reports: /tmp/brainstorm-critique-product-folder/{julie-yoo,april-dunford,matt-dixon,the-architect}.md

01Why now

Brand was canonicalized (v0.5). Generators now reach into brand/ for thesis. But several recent generation runs surfaced a class of fact brand/ can't carry — and the cost of leaving it un-canonicalized compounds with every new generator.

Payer-deck economics are nowhere

A Medicaid-MCO deck needs PMPM tiers, MLR impact from prior pilots, and reimbursement-code coverage. Brand can't carry numbers that change per contract.

EHR-integration claims drift

"We integrate with Epic via Vendor Services" — which version? which release track? which workflow? Generators hallucinate or omit. Yoo fact-check

Coverage matrices go stale silently

"Available in 38 states for commercial and MA, 14 states for Medicaid." Updates monthly; a stale number is a compliance risk.

Workflow integration ≠ clinical evidence

RCT results live in brand/proof/clinical-evidence.md. The actual workflow — EHR inbox, SMART app, alert triage — has nowhere to live.

Regulatory tailwinds rotate quarterly

CMS rules, state Medicaid waivers, ERISA decisions, drug-class shifts. Brand's cadence is wrong for facts that move every 90 days.

Composite numbers want a single source

The same readmission-reduction figure is hand-rewritten across decks, blog posts, case studies. Atomic per-cohort numbers can't supply blended/aggregated rollups. Dunford H

We define the sibling now, before generators accumulate ad-hoc fact lookups that drift across implementations — exactly the failure mode brand-folder canonicalization was meant to prevent.

02Goal

Define the canonical product/ folder that an AI-native digital-health company installs once, and from which every marketing-asset generator pulls operational and product facts predictably — same shape, frontmatter discipline, and slice-loading mechanics as brand/, plus stricter source-citation and decay rigor, plus actuarial-grade fields for late-stage proof-points.

  • Encode operational and product fact the way brand encodes durable thesis.
  • Be digital-health domain-specific — slot list reflects EHR, reimbursement, VBC, coverage by line of business, clinical workflow, regulatory tailwinds.
  • Be "OK to quote in a public-facing deck" by default — engineering-internal facts go elsewhere.
  • Encode source-citation rigor beyond brand — sources, denominator, validated_at, decay_window mandatory; methodology / comparator / CI for actuarial-grade facts.
  • Compose with brand and clients at generation time: brand × product × clients/{prospect}.

03Hard constraints

Rules the architecture must honor in every implementation. Each is enforceable — a generator, lint, or schema check fails on violation.

Sibling to brand/ and sales/, not nested. Top-level product/, single-tenant.
Single-org per repo. Multi-product = sub-folders within product/ OR separate repos (§15).
One shape, every digital health company. Identical layout across telehealth, RPM, behavioral health, digital therapeutics, payer-side, provider-side, condition platforms.
AI-first design. Primary consumer is generator agents (~95% of reads).
Frontmatter mandatory on every .md. Tiered minimums by confidence: level (§09). Dixon M1
"Marketing-quotable, not engineering-internal" — split gate. Dunford H
  Inclusion (4a): file is in product/ if a generator would quote it (in part or summary) in a public-facing artifact.
  Exclusion (4b — adversarial): excluded if pasting verbatim would (a) fail a fact-check OR (b) create competitive/legal/reputational harm. Operative test: "If a competitor's analyst found this file in a leaked grep, would that hurt us?" If yes, NOT product/. Kills roadmap.md, raw customer data, security incidents.
  Enforced at PR review, not at frontmatter parse — too contextual for a regex check.
No content duplication. A fact lives in exactly one file. brand/proof/case-studies.md references product/economics/... by slice path; never restates the number.
Every fact is sourced. sources: mandatory. sources[].kind enum is the union of brand's enum + product extensions: url | interview | doc | claim | contract-attestation | regulatory-filing | audit-attestation | vendor-attestation | payer-feed | claims-data. Architect S2
validated_at mandatory. ISO 8601 (YYYY-MM-DD); lint rejects other formats. Architect S6
decay_window required. Format <integer>d; lint rejects other units. Default 180d; per-directory overrides (§10). Architect S1
proof-product-link eval is gated on product/ existence. Skipped (not failed) when product/ is absent — permits brand-only orgs and the brand-before-product cutover gap. Architect E3
Provenance, confidence, status, slice-loading — same as brand. Reuse the shared loader (§13).
Clean-state cutover. Coordinated PR with brand canonicalization. No aliasing shim.

04Core commitments

Softer than hard constraints — the principles that explain why the architecture is shaped this way.

Fact, not fiction — the central commitment

Every file is a fact register. Narrative lives in brand/. The reviewer test:

"Could a sales rep paste any sentence from this file into a customer-facing artifact and have it survive (a) a fact-check AND (b) the company's disclosure standards?" — both clauses must be true.

Definition: fact register Dunford LOW

A fact register is a structured catalog of typed, sourced, dated assertions — each addressable as a slice, each carrying its denominator (when applicable), each with a decay window. It is not a narrative; it is a lookup table a generator queries by slice path.

Numbers live here once — including composite

Atomic per-cohort numbers at {folder}/{topic}.md. Composite/blended numbers are first-class facts at {folder}/{topic}-blended.md, with methodology disclosed. Brand never inline-composes math. Dunford H

Source-citation rigor is the delta

Brand can carry an unsourced positioning paragraph. Product cannot. Every claim is sourced or it doesn't ship.

Decay is encoded, not advisory

decay_window: is enforced — three-actor enforcement model in §15.2.

Generator-facing first

Files written so a generator pulls a slice and produces an on-brand, factually-correct sentence with no further interpretation.

Composition order is meaningful

brand sets the interpretive frame; product fills evidence slots; clients overlays per-deal filters. Reverse the order and the generator becomes a fact-stitcher, not a narrative composer. Dunford MED

clients/ is selection, not correction

clients/ selects which slices to pull and with what emphasis. It does NOT override product values. If clients contradicts product, that's a bug in product. Dunford MED

05Sibling map: brand × product × sales

The three durable folders an AI-native digital-health company installs at the repo root. Each owns a distinct kind of context. A marketing-asset generator composes from all three.

FolderOwnsCadenceReviewer test
brand/ Durable thesis. Positioning, narrative, messaging, voice, audiences, personas, market terrain, design, proof stories. Slow. Positioning ~2× / year. Messaging constantly. Narrative on strategy shifts. "Does this require reasoning to defend?"
product/ new Operational and product fact. PMPM, EHR footprint, coverage matrix, VBC structures, clinical workflow, engagement numbers, regulatory tailwinds. Mixed. Coverage monthly; regulatory quarterly; engagement half-yearly. "Survives a fact-check AND survives disclosure scrutiny?"
sales/ future sibling Deal-stage playbook. Pricing-with-discounts, talk tracks, deal-cycle playbook, MEDDIC fields, NDA-gated specifics. Per-deal. "Is this what a rep does mid-cycle, behind the scenes?"

Six boundary clarifications

  1. product/ vs brand/proof/ — numbers vs stories. Numbers (atomic AND composite) live in product/. Stories live in brand/proof/case-studies.md referencing via depends_on:. Composite numbers are first-class at {folder}/{topic}-blended.md with methodology.
  2. product/ vs engineering tree — quotable test. If a generator would quote it, product/. If only engineers/ops read it, engineering tree.
  3. Coverage ⊥ audiences Dunford MED. Coverage = "where can we legally operate?" (regulatory + LOB). Audiences = "who do we choose to sell to?" (vertical + segment). Orthogonal cuts, not duplicates.
  4. clients/ is composition-by-selection Dunford MED. Per-prospect cohort selection + competitive context + integration context. Never overrides product values. If clients contradicts product, fix product.
  5. Compliance straddles Yoo B2. brand/proof/compliance.md = the attestation we hold (HIPAA, SOC 2, HITRUST as proof story). product/coverage/accreditation.md = the coverage implication (HITRUST r2 required for Anthem). They co-reference.
  6. Clinical-evidence dependency is one-way Yoo B1. product/clinical/clinical-protocols.md MAY depends_on: brand/proof/clinical-evidence#trial-x to ground a threshold. Reverse forbidden.

Acknowledged gap: clients/ schema is the next sibling design Dixon H1

The composition contract assumes clients/{prospect}.md exists with required slots: discovery synthesis, internal-stakeholder map (mobilizer / talker / blocker), per-stakeholder priorities, prior-pilot history, current-vendor stack, deal stage, blockers/risks. Without that schema defined, "tailored deck" reduces to "templated deck with name find-and-replace." Out of scope here; named as a known gap.

09Tiered minimum frontmatter Dixon M1

Without this, the source-citation discipline produces a 40%-empty folder. With it, operators ship at low and enrich over time as evidence is gathered. Generators MAY filter on min_confidence:; default medium.

confidence:Required minimumUse when
lowid, type, slices, status, confidence, sources (≥1), validated_at, decay_windowInitial population — fact established but evidentiary detail not yet gathered. Generator-default-rejects unless explicitly opted in.
mediumlow + evidence_kind, denominator (when applicable)Cited in routine generator output (decks, blog posts, one-pagers, landing pages).
highmedium + methodology, comparator, analysis_provenanceLate-stage proof-points subject to actuarial / scientific scrutiny. Required for committee-grade decks.

12Contract merge semantics Architect E1

The single most important spec for v1 implementation. Without it, v1 ships with a loader that has to guess the contract shape.

Coordinated rename in brand

Brand's existing requires: field is renamed to brand_requires:; optional: to brand_optional:. Performed in the same coordinated PR as product v1 ship. No backward-compat shim.

Per-generator deep merge on distinct keys

When both files declare generators.generate-X, the merge is per-generator deep merge: brand_requires: from brand's contracts and product_requires: from product's contracts do not collide because they have distinct names.

Last-write-wins on scalar overrides

min_confidence, min_freshness, compose are last-write-wins (product overrides brand if it redeclares).

Loader signature extension Architect L3

The shared loader returns is_in_window: bool per slice (computed from validated_at + decay_window) and accepts a min_freshness: in-window | any parameter (default any, brand-backward-compatible). When min_freshness: in-window is set and any required slice has is_in_window: false, the loader refuses with a structured error naming the stale slice.
