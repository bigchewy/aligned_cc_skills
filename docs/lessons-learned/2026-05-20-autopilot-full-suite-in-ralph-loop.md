# Lesson: Recurring Full-Suite Runs Inside the Ralph Loop

**Date:** 2026-05-20  
**Symptoms:** Machine swap spike (1.5 → 9 GB in 90 s), load average → 14, Activity Monitor showing 9–10 parallel Node worker processes during autopilot runs.  
**10 prior fix attempts:** All targeted process-group kill signaling (setsid, negative-PID SIGTERM, watchdog, swap guard, blocked-gate). None worked because they addressed the wrong problem.

---

## Root Cause

Plans generated by the writing-plans skill routinely included a "Final full-suite verification" task as the last plan task. That task ran `npm run build` (= `next build --webpack`), which spawns a webpack worker pool sized to CPU count − 1 (~9 workers on a 10-core Mac). Each worker allocated 200–900 MB RSS. Combined: 1.5–9 GB swap in 90 seconds, CPU load spiking to 14+.

This task duplicated Phase 9 (verify), which already runs `npm run build` + full test suite after the ralph loop completes. The work happened twice: once inside ralph (no circuit breaker for mid-iteration memory pressure) and again in Phase 9.

## Why 10 Fix Attempts Failed

Every prior fix addressed the wrong layer:

| Fix # | What was changed | Why it didn't work |
|-------|------------------|--------------------|
| 1–9 | Process management (setsid, kill groups, swap guard, blocked-gate, etc.) | Node workers were children of the webpack process, not the claude process group; kill signals never reached them |
| 10 (866b709) | Added `npm test` / `npx jest` to SKILL.md prohibited list | Partial: didn't cover `npm run build`; didn't cover the "final verification task" category; critique layer never checked for this |

The process-management diagnosis was wrong from the start. The diagnostic logs clearly showed `survivors_in_group=0 system_node=0` after every iteration — no processes were leaking. The 9 nodes were in-flight during the iteration, not accumulated.

## The Three Independent Failure Modes

1. **Plan authoring:** SKILL.md prohibited bare test runners but not build commands. The "no final verification task" rule was implied but not explicit. The LLM classified Task 21 as a "verification gate" (not an "implementation task body") and skipped the prohibition.

2. **Critique layer:** The Verifier's autonomy-violations signal list covered paid API calls, Supabase Dashboard, OAuth, manual paste — not bare test/build/lint commands. Plans with Task 21 passed critique cleanly.

3. **Execution layer:** EXECUTE-PLAN.md guarded against bare `npm test` / `vitest run` but said nothing about `npm run build`. The executor ran the full build as specified.

All three had to fail simultaneously for the problem to manifest. They did, every time.

## The Fix (commit bff87be)

Three-layer fix, one change per layer:

1. **WRITE-PLAN.md override #7** — highest-visibility prohibition at plan authoring time; explicitly bans "final verification" tasks as a category error
2. **SKILL.md** — adds `npm run build`, `next build`, `tsc`, `npm run lint`, `eslint .` to prohibited commands list; adds explicit "do not create a final verification task" rule
3. **plan-critique-checklist.md + critique-panel-prompts.md** — adds full-suite test/build/lint commands and "Final verification" task patterns to the Verifier's autonomy-violations signal list (HIGH severity)
4. **EXECUTE-PLAN.md** — adds skip-and-note rule for build/lint commands; adds immediate-✅ rule for tasks whose entire purpose is full-suite/build/lint

## What to Check If This Recurs

If a future plan generates a task containing `npm run build` or a "Final verification" heading:

1. Check whether the three prohibitions landed in the prompt the plan writer actually received (read `plan.sh` output to verify SKILL.md path was passed)
2. Check whether the Verifier critique caught it (look at critique round output for [Verifier] HIGH findings)
3. Check whether EXECUTE-PLAN.md's skip rule fired (the executor's completion message should say "Skipped — Phase 9 scope")

If all three layers failed simultaneously again, the LLM is pattern-matching on design-doc language that signals "integration/final" and overriding the rules. In that case, consider adding a pre-plan check in `phases/plan.sh` that greps the generated plan for prohibited commands before the critique phase runs.

## Key Diagnostic Tool

The real memory leak vs. transient-pressure distinction is visible in `$WORKTREE/.ralph-log.processes`. If `survivors_in_group=0 system_node=0` appears after every iteration, there is NO persistent process leak — the problem is peak concurrency within a single iteration. Do not spend sessions on process-group kill logic if that pattern holds.
