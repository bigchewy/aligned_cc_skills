Skill Orchestration

How Aligned plugin skills connect, delegate, and orchestrate

22 skills across three tiers: 15 entry points you invoke directly, 3 pipeline steps invoked as part of a workflow, and 4 support skills typically invoked by other skills.

The Aligned plugin adds structured skills to Claude Code. Each skill is a slash command. Some form a sequential pipeline; others are standalone tools you reach for when needed. Click any card to see how the skills work internally.

Development Pipeline

The primary workflow. Brainstorm a design, write an implementation plan, execute it, then merge. Each step feeds the next.

  • /brainstorming Design, strategize, research, author, or plan
  • /writing-plans Implementation plan with critics
  • /executing-plans Autonomous task execution
  • /finishing-a-development-branch Merge, deploy, or discard

Advisor & Frameworks

65 expert personas and 138 structured frameworks. Use them, extend them, or test content against them.

  • /use-advisor Adopt an expert persona
  • /use-framework Run a framework phase by phase
  • /find-potential-advisors Research new advisor candidates
  • /add-advisor Create a new advisor
  • /add-framework Add framework to an advisor
  • /persona-panel Test content against buyer personas

Quality & Maintenance

Keep the codebase healthy. Standalone tools invoked when you need them, not as part of the pipeline.

  • /codebase-audit Multi-dimensional code audit
  • /root-cause-analysis Investigate bugs or business problems
  • /eval-audit Find untested LLM behavior changes
  • /kanban-resolve Triage accumulated Kanban items

Setup & Tooling

Bootstrap projects and extend the plugin. Typically invoked once per project or when adding capabilities.

  • /kickstart Scaffold a new project

Brainstorming — Mode Detection & DesignEntry Point

Every brainstorming session starts with mode detection, dispatches a background project scan, then follows a mode-specific Q&A process. All four modes converge at the post-design phase.

Router

  • Software mode signals: features, APIs, architecture, code, testing, data models
  • Authoring mode signals: curriculum, program design, sequence content, exercise sequencing, framework prompt authoring, voice migration, strategy, sales, positioning, pricing, decisions, stakeholders, "why isn't this working"
  • Research mode signals: literature review, evidence map, comparative review, instrument selection, framework comparison, KB design
  • Roadmap mode signals: roadmap, prioritization, portfolio, "what to build next", multi-feature build, "too big for one brainstorm"
  • Disambiguation: Software vs Authoring on deliverable shape (code vs content); Authoring vs Research on output (arrangement vs evidence map); Authoring vs Roadmap on scope (single deliverable vs multi-feature portfolio)
  • Tiebreaker: environment — code repo suggests Software, knowledge folders suggest Research, content registries suggest Authoring, prior roadmaps suggest Roadmap
  • Project Scanner: dispatched immediately in background — does not block Q&A

Research Mode

  • 5-phase process: scope & question framing → corpus survey → comparative synthesis → Skeptic Pass critique (inline) → ranked recommendations with caveats
  • Skeptic Pass: inline critique that stress-tests every claim before recommendations are produced — reduces false confidence in synthesis
  • Deliverable: research memo or KB artifact (evidence map, ranked synthesis with caveats — no arrangement output)

Authoring Mode

  • Domain-advisor panel: selected per content type (curriculum design, framework prompt authoring, exercise sequencing)
  • Optional Research sub-phase: file-mediated sub-agent fork — Authoring writes a question to /tmp/brainstorm-context-{topic}/research-{slug}-question.md, the Research sub-agent answers via research-{slug}-synthesis.md
  • Failure handling: if synthesis is missing, empty, or lacks confidence/caveat fields, Authoring proceeds without the input rather than blocking
  • Deliverable: sequenced design doc (curriculum, framework prompts, exercise programs)

Roadmap Mode

  • Strategy advisors: Christensen, Rumelt, Eric Ries (plus Cagan and Sisney when their advisor files are present — runtime-checked, no hard dependency)
  • Two-artifact output: roadmap + spawn-list portfolio. Each portfolio entry is a "spawn brief" (topic, mode, deliverable, scan emphasis) that seeds a future brainstorm
  • Critique panel: dispatched against the roadmap-critique-checklist (9 criteria covering sequencing, dependencies, capacity, and risk)
  • Deliverable: roadmap + spawn-list portfolio whose entries seed future single-mode brainstorms

Post-Design (All Modes)

  • Design doc: written to docs/plans/YYYY-MM-DD-topic-design.md
  • session-document-generator: produces tabbed HTML visualization from design doc
  • Critique panel: 2-4 advisors evaluate in parallel; fact-checker verifies all codebase claims
  • Visualization refresh: re-dispatched if design doc changed after critique

Autopilot — Unattended PipelineInfrastructure

autopilot.sh orchestrates five sequential phases from design doc to verified branch. You walk away after launching it. Each phase writes a sentinel file so the script can resume after interruption.

  • Phase 1 — Plan: invokes claude -p with writing-plans workflow; writes plan path to sentinel
  • Phase 2 — Worktree: creates feature branch + worktree, installs deps, merges main
  • Phase 3 — Ralph loop: delegates to run-ralph.sh; each iteration is a separate claude -p instance executing one task
  • Phase 3.5 — Mockup fidelity: iterative loop (up to 5x) comparing implementation against HTML mockups
  • Phase 4 — Verify: runs tests, build, evals; writes .finish-status with SUCCESS or FAILED

Ralph Loop — One Task Per Claude InstanceLoop

run-ralph.sh spawns a fresh claude -p per iteration, each executing exactly one plan task. Progress is preserved via checkmarks in the plan file. Also available standalone outside autopilot.

  • One task per instance: each Claude invocation reads the next unchecked task, executes it, marks it done, commits, then exits
  • Sentinel file: when all tasks are done, writes .ralph-done and exits
  • Timeout watchdog: 15-minute SIGKILL per iteration; 5 consecutive timeouts abort
  • Failure cap: 3 consecutive non-zero exits abort the loop

ResumabilityResilience

Safe to re-run after interruption. Each phase checks for its completion artifact before executing; completed phases are skipped automatically.

  • .autopilot-plan-path: sentinel with design doc + plan paths — Phase 1 skipped if present
  • Worktree directory: Phase 2 checks existence; if found, skips creation but still merges main
  • Checkmarks in plan: Ralph loop picks up from the first unchecked task
  • .mockup-clean: Phase 3.5 skipped if present
  • .finish-status: Phase 4 skipped if SUCCESS; re-run if FAILED

Writing Plans — Research & CritiquePipeline

Explores the codebase, writes a detailed implementation plan with verified file paths, then runs a 2-critic panel before committing. Secondary entry point: users with an existing design spec can invoke /aligned:writing-plans directly.

  • Codebase research: reads architecture.md, verifies every file path via Glob/Grep/Read
  • Plan location: always committed to main's docs/plans/ — survives branch discard
  • Round 1 critics (parallel): The Architect (codebase alignment, gaps) + The Verifier (every claim verified, design fidelity)
  • Aggregation sub-agent: merges reports into actionable summary under 1500 words
  • Round 2 (conditional): only if medium/high issues; scoped to changed sections; haiku model

Executing Plans — Autonomous Task CyclePipeline

Loads the plan from main, verifies it's on a feature branch, and executes all tasks autonomously. Only stops on blockers or verification failures.

  • Branch guard: refuses to run on main/master — requires a feature worktree
  • Autonomous mode: executes all tasks without pausing for review
  • LLM surface check: if a task touched prompts, runs evals immediately
  • Bug board: out-of-scope bugs logged to docs/kanban/todo/
  • Archive: plan + design doc moved to docs/plans/completed/

Finishing a Development BranchPipeline

Always runs from the main repo, never inside a worktree. Applies after both autopilot and hands-on paths. Runs a sequential checklist before presenting merge options.

  • Deployment audit: scans for Vercel pitfalls — CRITICAL findings block merge
  • Test + build gate: both must pass before proceeding
  • LLM eval: auto-runs if LLM behavior surface files changed
  • Architecture doc: updates docs/architecture.md if structure changed
  • Code simplifier: read-only agent scans diff; filed to Kanban (non-blocking)
  • Code reviewer: reviews implementation against plan and coding standards
  • Mockup fidelity: compares implementation against HTML mockups
  • 4 options: merge locally, deploy + smoke test, keep as-is, discard

Quality & MaintenanceQuality

Four independent skills for keeping the codebase healthy. Invoked standalone, not as part of the development pipeline.

  • codebase-audit: multi-dimensional audit with 5 parallel workers (code quality, tests, security, dead code, architecture). Findings feed kanban-resolve.
  • root-cause-analysis: systematic investigation for software bugs and business problems. Supports low (default) and high severity with multi-agent mode.
  • eval-audit: detects LLM behavior surface changes without eval coverage. Hook-prompted ([EVAL AUDIT] tag suggests running it; you decide).
  • kanban-resolve: triages and resolves accumulated Kanban board items in one pass. Dispatches kanban-triage agent for root cause analysis on each item.
